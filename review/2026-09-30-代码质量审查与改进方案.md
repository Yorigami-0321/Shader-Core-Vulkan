#### 🟠 G-04 · `04-SPEC:86` 对 `#include` 的描述仍是错的（延续 F-05）

**现状**（`docs/04-SPEC.md:86`）：

```java
IncludeProcessor.java    // 处理 #include（OF: 相对路径；Iris: namespace:path）
```

**事实**：`#include` 只有**绝对（`/` 前缀）**与**相对**两种形式，**不存在 `namespace:path` 语法**。

**影响**：这是全仓**唯一一处"文档比实现更不可信"**的地方，且在 P2.3（include 展开接主线）
刚落地之后，误导读者的概率显著上升。

**建议**：删除 `；Iris: namespace:path`，与 `IncludeResolver` javadoc 对齐。
**成本**：5 分钟（⚠️ `docs/` 归 env-1，需转交执行）。

#### 🔵 G-08 · bridge 层反向依赖业务层（设计层观察）

**事实**：`bridge/FrameApi` 直接引用了业务包：

```java
private static java.util.List<dev.vkdisp.shadow.LightSpaceList.Entry> lightSpaceList;   // :124
boolean deferredChain = useScene && dev.vkdisp.VkDispVirtualPack.hasDeferredProgram();  // :625
```

两处都用了**全限定名**而非 `import`——这恰恰说明作者意识到了跨层引用，用 FQN 绕开了 import 规则。

**影响**（不是红线违规，T5 只约束"业务包 → renderpearl"这一个方向）：
- `bridge` 原本是**单向边界**（业务 → 原版），现在出现反向边，形成包级循环依赖；
- `FrameApi` 变得不可独立测试（要拉起业务层静态状态）；
- FQN 写法让这类依赖**在 import 列表里不可见**，审查时容易漏。

**建议（择一）**：
1. 把所需状态**参数化**：`drawFullscreen(label, params)` 的 `params` 增加
   `boolean allowDeferredChain` / `List<Entry> lightSpaces`，由业务层在调用点传入；
2. 或维持现状但在 `docs/06-MIGRATION §2.1` 明文登记「bridge 允许读取业务层的只读状态视图」，
   并把 FQN 改回 `import` 让依赖显式化。

**成本**：1–2 小时（方案 1）。
