## 3. 规范符合性缺口

### 🟠 F-02 · `07-CONSTRAINTS §3.2` 空安全要求完全未落地

**条款原文**（`docs/07-CONSTRAINTS.md:161-168`）：

```java
// 所有可空返回值必须标注（NeoForge 用 org.jspecify）
public @Nullable RenderPipeline compileProgram(ProgramStage stage) { ... }
```

**实测**：

- 全仓库 `@Nullable` 出现次数：**0**
- 全仓库 `return null` 出现次数：**30**（分布于 `OptionText`、`PackOptions`、`ConstEvaluator`、`FragmentOutputAdapter`、`GlslDeclaration`、`OnGlslTranslator`、`VertexLayout` 等 13 个文件）

**定性**：这是**纯规范执行缺口，不是缺陷**——抽查的 `return null` 语义均合理且被调用方正确兜住，例如：

```java
// bridge/DeviceApi.java:57-62 —— "设备未就绪"语义，调用方显式抛错而非传播 null
private static DeviceInfoView deviceInfoOrNull() {
    GpuDevice device = RenderSystem.tryGetDevice();
    if (device == null) { return null; }
    ...
}
// 调用方（同文件:50-55）
if (view == null) {
    throw new IllegalStateException("vkdisp: GPU device not ready yet (...)");
}
```

**影响**：静态分析/IDE 空安全推断失效；后续升级（26.4 换签名）时，30 处 null 传播点缺少机器可读的契约标注。

**建议（二选一，不要留空）**：
1. 为 30 处方法补 `@Nullable`（`org.jspecify`），成本约半小时；或
2. 修订 `07-CONSTRAINTS §3.2`，明确本工程**不**采用 jspecify 标注，改用"私有 `xxxOrNull()` 命名约定 + 调用方显式判空"。

> ⚠️ 选 2 时必须在 §3.2 写明判据，否则下一次审查还会命中同一条。

## 4. 文档-实现一致性

### 🟠 F-05 · `04-SPEC.md:86` 对 `#include` 的描述与实现相悖，且事实本身有误

**文档现状**（`docs/04-SPEC.md:86`）：

```java
IncludeProcessor.java    // 处理 #include（OF: 相对路径；Iris: namespace:path）
```

**实现现状**（`src/main/java/dev/vkdisp/glsl/preprocess/IncludeResolver.java` 类注释）：

> 绝对路径前导 `/` → 相对 `shaders/` 顶层；相对路径 → 相对当前文件目录

全仓库源码 `grep -rn "namespace"` 命中的 3 处**全部在 `pack/properties/IdMapProperties.java`**，那是 `block.properties` 里**实体引用**（`minecraft:stone`）的语法，与 `#include` 无关。

**结论**：
1. **实现是对的**——`#include` 只有「绝对（`/` 前缀）」与「相对」两种形式；
2. **文档是错的**——Iris/OF 官方 `#include` 本就不存在 `namespace:path` 语法，这一句是把 `IdMapProperties` 的实体引用语法**误植**到了 include 上；
3. 该错误会直接误导下一个实现者（尤其 P2.3 汇合时）。

**建议**：删除 `；Iris: namespace:path`，与 `IncludeResolver` 的 javadoc 对齐。这是**唯一一处文档比实现更不可信**的地方。

### 🔴 F-01 · 已完成里程碑的全部验收证据不在仓库（唯一高危项）

**事实链**：

1. `CHANGE_LOG.md` 的每条里程碑条目，都以"证据"形式引用具体文件与 sha256，例如：
   - `p32_vanilla_camera2.log`（sha256 `9d80b554571fd991…`）
   - `p33_shadow_sample.png`（sha256 `be16fe8cf5df7804…`）
   - `p32_final_A.png`（sha256 `22dd9a43…`）vs `p32_final_B.png`（sha256 `15048894…`）
   - 以及"像素计数"结论：受影绿 `(0,89,0)` 19,584 像素、阴影覆盖率 39.8%……

2. 这些文件被声明存放于 `tools/vulkan-local/evidence/`（`CHANGE_LOG.md:36` 自述"证据目录 `tools/vulkan-local/evidence/`，被 `.gitignore` 覆盖、不入库"）。

3. **实测：该目录当前不存在。**

   ```
   $ ls tools/vulkan-local/
   env.sh  pkg  prefix  vk_smoke.py        # 无 evidence/
   ```

   `tools/` 整个目录未被 git 跟踪（`git ls-files tools/ | wc -l` → `0`），`evidence/` 也不存在。

**影响（这是本报告最需要决策的一条）**：

- **验收结论不可复核**。`08-TESTING.md` 里 P0–P3 的通过标准，对外呈现为"已通过"，但支撑它的日志、截图、像素统计**全部无法获取**。

- **最强的那类证据最先失效**。像素级判据（如"0.35 调暗系数精确吻合 → 89 = 255×0.35"）说服力最高，但它是**二进制 + 一次性产出**，丢了就只剩结论文字。
- **跨环境协作放大风险**。本项目是多环境分工（`18-PARALLEL §7.5`），且已发生过"重复劳动"（本地改动与远端逐字节一致）。证据不入库时，第二个环境**无法判断某条结论是否已被验证过**，只能重跑。

**建议（按成本从低到高，任一即可消除风险）**：

1. **最低成本**：把每条里程碑的**证据摘要**以纯文本入库（新建 `review/evidence/` 或 `docs/` 的证据附录）——只留日志关键行 + 文件 sha256 + 判定结论 + 一行"如何复现"。二进制留本地。
2. **中成本**：截图降采样为小尺寸 PNG 入库（每张 < 100 KB，几十张量级对仓库无压力）。
3. **最高成本**：建立结构化的证据登记表（每条 = 里程碑 / 证据类型 / 结论 / 复现命令 / 存储位置），把 `CHANGE_LOG` 的"测试结果"段改为引用该表。

> 本报告不认为这是"开发者的失误"——不入库二进制证据是常见的仓库瘦身选择。但**结论与原始证据必须二选一入库**，不能两者都在仓库外。

### 🔵 F-09 · 热路径每帧堆分配（观察项，非缺陷）

`FrameApi` 中 `lightSpaceMatrix()`、`placeholderCamera()`、`cameraMatrix()` 均在 `RenderFrameEvent.Post`（**每帧一次**）的调用链上，每次新建 `Matrix4f` 与若干 `Vector3f`，估算 **6–8 个对象/帧**（60 FPS 下约 400 对象/秒）。

**为什么不定性为缺陷**：按项目自己的纪律——`17-NATIVE §3.2` 将这类优化归为"必须由实测数据驱动"，`T14`/`X14` 明确禁止"凭感觉优化"，`08-TESTING §8.1` 要求"达标即停"。**在没有帧时间数据之前，改它就是违规**。

**但它对应一个真实的证据缺口**：`08-TESTING §8` 的"**不开包：帧时间相对纯原版 ≤ +2%（P0 起必过）**"目前**没有任何实测数据**（`CHANGE_LOG` 各条只记录构建/测试/画面判据，无帧时间）。P0.3 已经上屏、P1.1 已在每帧改 uniform，这一项**早该有数字了**。

**建议**：下一次 WSL 运行时，顺手用 F3 屏采三组中位数，把 `17-NATIVE §7.3` 的基线表回填。这是"完成 P0"的最后一块拼图。
