### 1.2 已证伪的部分（路线级，不是缺陷）

🔴 **P4.4-a「零 mixin 覆盖原版program」已被实跑否决**（`evidence/p4x4a-vanilla-override-rejected.md`）。

根因是**接口契约结构性不兼容**，不是实现bug：

| 契约面 | 第三方 pack（BSL）| 原版管线固定值 |
|---|---|---|
| 顶点输入 | `vec4 UV0` / `mc_Entity` / `mc_midTexCoord` | `DefaultVertexFormat.BLOCK`：无这些字段 |
| varying | 9 个 | `core/terrain` 固定 5 个 |
| 颜色附件 | 多输出 gbuffer | `ColorTargetState.DEFAULT` = **单附件 RGBA8** |
| uniform | 需相机矩阵 + 太阳方向 | `globals.glsl` 仅 9 字段，**两者都没有** |

**推论（本轮最重要的一条）**：
换 program 文本 ⇒ 必须同时换**顶点格式**与**附件数** ⇒ 零 mixin 下两者都无入口
⇒ **「接管地形渲染」和「注入原版管线做后处理」是两个不同量级的工程。**
已交付的是后者，天花板就在这里。

> **补记（2026-10-02 晚，已并入正文档）**：本条推论已直接导致 `07` M1 从
> 「全局只许 1 个注入点」松绑为「管线装配层 + 登记制 + 可关闭制 + 逐个开启」，
> 并登记为 **GAP-003 / GAP-004**。**§3.1 的部分问题因此已有答案，但并未全部关闭。**

## 3. 待调研的开放问题（🔴 尚未有结论，登记为问题不是立场）

### 3.1 渲染架构：Rust 引擎 vs 原版/纯 Java（🔴 最高优先级）

用户明确要求**先调研再定**。需要查清、目前**完全没有结论**的问题：

- [ ] 「Rust 重写引擎」的**具体含义**是什么？—— 是替换原版整个渲染后端（frame graph + 管线 +
      资源绑定全自己管），还是只接管其中一层（gbuffer 生成 / 上采样 / 后处理编排）？
      ⚠️ 这两者工作量差**一到两个数量级**，且决定后续一切。
- [x] ~~原版 26.3 的渲染后端能替换到什么程度？~~ ✅ **2026-10-04 已答**：
      ① 旧记载「`FrameGraphSetupEvent` **没有插 pass 入口**」= **错**（已核实 `getFrameGrapBuilder()`
      且触发点在 `frame.addPass("clear")` 之前）；② 「`putIfAbsent` 不能覆盖 location」成立，
      但官方 `PipelineModifier` 会自动改写 location ⇒ **该缺口有官方旁路**。
      ⇒ 换管线**不一定**要接管 draw。三处缺口的官方通道见 `07` §1.4.2。
      ⛔ 整体替换后端（L4）撞 X24/T3/L7，建议否决。
- [ ] Rust 与 Java 的边界怎么切？JNI 逐帧调用 vs 批量命令缓冲 vs 纯 Rust 渲染线程 + Java 只管游戏逻辑？
      ⚠️ 逐帧 JNI 会引入新的性能瓶颈，可能比纯 Java 更慢——**这一点必须有实测依据，不能凭直觉**。
- [ ] 「重写引擎」与「M1 只许一个 mixin」是否冲突？
- [ ] 若走 Rust，现有 P4.x 已跑通的转译层（190 个 program）是**保留**还是**重写**？
      —— ⚠️ 这是最大的沉没成本问题，必须明确回答。

> **部分进展（2026-10-02 晚）**：
> - ✅ 「M1 只许一个 mixin」的冲突**已解除**（M1 松绑为登记制 + 可关闭制）。
> - ✅ 「Rust 逐帧 JNI 会不会更慢」已有**制度化答案**：FFM 优先（`07` T19），
>   接口**按批不按条**（T18），且冷路径已列入 G 系列实测范围（`glsl/` 转译 + `pack/` 解析）。
> - ❌ **仍未裁决**：是否要**整体替换渲染后端**（而非接管一层）。这是本文最大未决项。

      4.5/5 是否为已发布版本或路线图命名。（**不许凭印象写版本号**）

> ⚠️ **与三支柱的关系**：若 DLSS 只能二选一，就与「兼容完整」（最高支柱）**直接冲突**，
> 按 `07` X27「不许为性能牺牲兼容」必须先解决这个矛盾才能动 DLSS。**本文不替用户决定。**

> 🟢 **裁决结论（2026-10-04，用户拍板）：完全不做 DLSS，不纳入考虑范围。**
> 本节以下内容**仅作该裁决的依据留档**，不再是待办。

> **支撑理由（调研已完成，2026-10-04）**：
> 1. **许可证是硬否决项**：`NVIDIA RTX SDKs LICENSE` **Clause 4.e** 原文禁止
>    「use the SDK in any manner that would cause it to become subject to an open source software license」
>    ⇒ DLSS 运行时**不能进 MIT 分发物**；另有 4.b 禁独立分发、4.g 赔偿义务。
>    （Streamline **框架层**是 MIT，但 DLSS 插件二进制不在其覆盖范围内。）
> 2. **Vulkan 后端拿不到完整能力**：官方文档明说 Dynamic Multi Frame Generation
>    「support is currently limited to D3D12 only」；帧生成还依赖 Windows 独占的 HWS。
> 3. **无现成参考可继承**：MIT 许可的 Minecraft+DLSS 项目仅 2–3 个且 star 全 0–1；
>    2 个无 LICENSE；star 最高的 Radiance 是 GPL-3.0 且完全不含 Streamline 代码。
> 4. **与三支柱冲突**：官方要求 SR「as close to the start of post-processing as possible」，
>    而 BSL/Complementary 的重度后处理正在那之前；且 DLSS 与 shader 包共存**无任何官方结论**。
>    按 X27「不许为性能牺牲兼容」，放弃 DLSS 是唯一不牺牲兼容柱的选择。

> 📌 **版本号留档**（供日后万一被问起）：DLSS **4.5 已发布**（2026-01-06 CES 2026）；
> DLSS **5 未发布**（2026-03-16 公布，官方口径「arriving this fall」，即 2026 秋季）。
> 二者**都不是 SDK 版本号**（SDK 侧版本线是 Streamline 2.x）。
