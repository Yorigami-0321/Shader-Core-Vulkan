# 17 · 性能预算与原生实现（Rust vs Java 实测方案）

> **授权来源（用户指令，2026-10-02，最高优先级）**：
> 「目的依旧是**高性能，稳定，以及保持兼容性让 optfine/iris 着色器完整的运行在 vulkan 上**。
> **接下来需要测试 rust 和 java 原生实现的性能差异。**」
>
> **本轮变更（相对 2026-09-29 版）**：本文从「C++/Rust 是未验证的可选项、冷路径一律纯 Java」
> 改写为「**冷路径（转译与预处理）进入 Rust vs Java 实测流程**」。
> 上一版把「冷路径」直接等同于「不许上原生」，是**推理过度**——冷路径决定的是
> **切包等待时长**（用户体验），不是帧率（帧率只由热路径决定）。
> 两者是**不同的优化目标**，本版把它们分开处理。
>
> 配套：`04-SPEC.md`（组件清单）、`07-CONSTRAINTS.md`（T13/T14/T16、**M1 mixin 边界**）、
> `08-TESTING.md` §8–§9（性能与原生验收）、`12-GAP-STRATEGY.md`、`01-DEV-LOOP.md`。

## 0. 三支柱与它们各自的度量（本轮总纲）

| 支柱 | 含义 | **唯一度量** | 优化对象 |
|---|---|---|---|
| **兼容** | OptiFine/Iris 格式着色器**完整**跑在原版 Vulkan 上 | pack × program 兼容矩阵通过率 | 功能覆盖，**不是速度问题** |
| **稳定** | 不崩、不闪、不静默降级、不泄漏 | 崩溃/validation error 计数 = 0；1h 内存增量 | 边界与生命周期 |
| **高性能** | 帧时间贴近原版；切包等待可接受 | 帧时间（ms/帧）、冷路径墙钟时间（ms） | 热路径 **和** 冷路径，见下 |

**关键区分（本版的认知修正）**：

```
帧时间（FPS）      ← 只由 🔥 热路径决定。冷路径再快，一帧内跑完就是 0 收益。
切包/加载等待      ← 只由 ❄️ 冷路径决定。热路径再快，也不会让编译少花 1 秒。
稳定性             ← 由边界条件与资源生命周期决定，与语言无关。
```

⇒ 「Rust 能让游戏跑更快吗」和「Rust 能让切包从 4s 变成 1s 吗」是**两个不同的问题**，
必须分别测量、分别下结论。旧版文档把二者混为一谈，导致冷路径优化被整体否定。

## 1. 纪律一：参考先行（动手前必须先查，且合规是第 0 步）

> 本节**沿用旧版全部内容，不删减**。合规闸门（许可证核对比优劣优先）仍然生效。

### 1.1 规矩

**任何一部分（解析器 / 转译器 / 编排 / GUI / 原生绑定）开工前，必须先做一轮参考调研。**
没有调研结论，不许动手写实现。

> 理由：本项目做的是「别人没做过的事」（OF 格式 → 原版 Vulkan），
> 但**每一块砖都有人做过**（预处理器、词法器、UBO 打包、帧图、管线缓存、FFI 桥）。
> 自己从零想，产出的一定比社区最成熟的实现差一个档次。

### 1.1.1 🔴 调研的第一件事是判合规，不是判优劣

**这条凌驾于其它所有调研标准之上。** 找参考时的**正确顺序**：

```
第 0 步（闸门）  这个参考的许可证是什么？→ 能不能合法地用在我的 MIT 工程里？
                ↓ 不能 → 直接放弃这个参考，换下一个候选（不要再看它的代码）
                ↓ 能   → 继续
第 1 步          它怎么做的？（做法 / 数据结构 / 边界条件）
第 2 步          它为什么这么做？（设计动机 / 踩过的坑）
第 3 步          我们的差异点是什么？（为什么不能照搬）
```

**本项目（MIT）的判合规要点**：

| 参考的许可证 | 能否并入本项目 | 能带走什么 | 不能带走什么 |
|---|---|---|---|
| **MIT / Apache-2.0 / BSD-2/3** | ✅ 可以（保留署名） | 代码 + 思路 | — |
| **LGPL-3.0** | ❌ 不可并入 | ✅ 思路、做法、事实性信息 | ❌ 任何代码行 |
| **GPL-3.0** | ❌ 传染，不可并入 | ✅ 思路、做法、事实性信息 | ❌ 任何代码行 |
| **PolyForm Shield / 非竞争类** | ❌ 不可 | ⚠️ 连"借鉴"都要谨慎，见 L11 | ❌ 代码，且不得做集成 |
| **All Rights Reserved** | ❌ 完全不可 | ❌ 什么都不要带走 | ❌ 全部 |
| **无 LICENSE 文件** | ⚠️ **默认 ARR**，视为不可用 | ❌ 什么都不要带走 | ❌ 全部 |

> ⚠️ **两个高频陷阱**：
> 1. **"GitHub 上能看见" ≠ "能用"**。没有 LICENSE 文件的项目默认保留所有权利，
>    跟 ARR 一样不能碰。
> 2. **"许可证写 GPL，但有例外条款"**（如 IrisShaders 的 glsl-preprocessor）——
>    例外条款往往只放开特定用途，**不等于对本项目放开**。这类情况**一律按禁止处理**。

**查证顺序（按可信度）**：仓库根 `LICENSE`/`LICENSE.md`/`COPYING` ← 最权威，只信这个；
源码文件头 `SPDX-License-Identifier`；平台页面 / README 的 License 章节 ← 常有错，仅作线索。

**拿不准时的默认动作**：**当作不能用**，只读思路。

## 2. 纪律二：性能预算（先定数字，再谈实现）

### 2.1 为什么必须先定

「高性能」「兼顾性能」是形容词，不是验收标准。**没有数字，就无法判断优化有没有用、能不能停。**

### 2.2 预算表（框架 GPU 本版）

| # | 场景 | 目标 | 测量方式 | 优先级 |
|---|---|---|---|---|
| **B1** | **不开包**（模组已加载但未启用） | 帧时间相对纯原版 **≤ +2%** | F3 屏 / Spark，同场景同视角，3 次取中位数 | **P0 必过** |
| **B2** | 开包（中等包，如 BSL） | 帧时间 **≤ 同机 Iris+OF 的 110%** | 同场景对比 | P2 起 |
| **B3** | **冷路径：全部 program 解析 + 转译** | **≤ 1 秒**（中等包） | 分段计时日志 | **P0 必过（本轮强化）** |
| **B4** | **包切换（含编译到就绪）** | **≤ 2 秒**（中等包，缓存命中 ≤ 0.5s） | 计时日志 | **P0 必过（本轮强化）** |
| **B5** | 首帧编译 | 无 **> 200ms** 的单帧卡顿 | 帧时间直方图 | P3 起 |
| **B6** | 内存 | 1 小时无持续增长；常驻增量 **≤ 200MB** | 任务管理器 / JFR | P1 起 |
| **B7** | 换维度 / 资源重载（F3+T） | 不崩、不闪烁（P4.6 闭环后零空窗） | 截图序列 + 日志 | P3 起 |

> **B1 仍是本项目最重要的性能指标**：一个着色器模组最不能被接受的就是「不装包也掉帧」。
>
> **B3/B4 是本轮新增的强化指标**：用户新目标把「高性能」写在了首位，而切包等待
> 是用户唯一能明确感知的性能指标。旧版文档只定 B1/B2，冷路径没有预算 ⇒ 无法管理。
> 已知现状：BSL 冷路径 1861ms（P4.5 三层缓存优化后），**距 B4 的 2s 已很接近**，
> 换更大的包（Complementary）必然超标 ⇒ 冷路径优化有明确的现实压力。

### 2.3 预算怎么用

```
① 实现一版（默认纯 Java，能跑通就行）
② 测 → 记录实测值（分环节，不只记总数）
③ 超预算 → 定位到具体环节（§3 热度分级）
④ 只优化超预算的那个环节
⑤ 再测 → 达标即停，不要继续优化
```

**达标即停。** 优化到预算内还继续做，属于未经授权的范围扩大（`07-CONSTRAINTS.md` X12）。

## 3. 纪律三：热度分级（决定优化目标，不禁止优化）

### 3.1 核心判断：**看调用频率 + 看用户可感知的等待时长**

| 路径 | 触发时机 | 频率量级 | 用户感知 | 允许的实现 |
|---|---|---|---|---|
| 🔥 **热路径** | 每帧 / 每区块 / 每顶点 | 10³–10⁷ / 秒 | 直接决定 FPS | 极致：无分配、无装箱、无字符串拼、无反射 |
| 🌤 **温路径** | 切维度、改选项、资源重载 | 几次 / 分钟 | 明显卡顿 | 合理：可分配、可读优先 |
| ❄️ **冷路径** | 首次解析 pack、预处理、转译、首次编译 | **一次 / 每包** | 切包等待秒数 | 清晰优先，**但受 B3/B4 预算约束** |

### 3.2 本项目的具体分级（2026-10-02 重标）

| 环节 | 分级 | 影响的指标 | 说明 |
|---|---|---|---|
| 顶点属性拼装 / 格式转换 | 🔥 **热** | B1 / B2 | 每顶点一次 |
| uniform / UBO 写入 | 🔥 **热** | B1 / B2 | 每帧多次 |
| 管线缓存查找（hash 键构造） | 🔥 **热** | B1 / B2 | 每 draw 一次 |
| 矩阵运算 / 视锥剔除辅助 | 🔥 **热** | B1 / B2 | 每帧大量 |
| 纹理状态切换 / 描述符集绑定 | 🔥 **热** | B1 / B2 | 每 pass × 每资源 |
| **GLSL 预处理 + 转译（`glsl/`）** | ❄️ **冷** | **B3 / B4** | 🔴 **本轮 Rust 实测对象**。BSL 全包 190 stage，转译 8 段流水线，串行 CPU 密集 |
| **OF 包解析（`pack/`）** | ❄️ **冷** | **B3 / B4** | 🔴 第二实测对象（properties/options 定稿 + program 清单） |
| 管线首次编译 | ❄️ **冷** | B4 / B5 | 走原版通道 + `PackCompileCache` |
| 包切换 / 资源重载 | 🌤 **温** | **B4 / B7** | P4.5 已异步化（3970→1861ms） |
| 选项 GUI 构建 | ❄️ 冷 | 无 | 打开时一次 |

> **本轮修正的旧结论**：旧版写「解析器/预处理器/转译器全是冷路径 ⇒ 用 Rust 重写帧率收益为零
> ⇒ 禁止上原生」。这个推理**只对了一半**：帧率收益确实为零，但它**不代表没有收益**——
> 它影响的是 B3/B4 的切包等待。正确的表述是：
>
> **「Rust 不能改善帧率；Rust 可能改善切包等待。是否值得做，由 §5 的实测决定。」**

## 4. 原生分层架构（可执行，非假设性）

> ⚠️ 与旧版不同：**本节现在是可执行的规范**，不是备忘。
> 但它仍然受两条硬约束：**§5 的实测门槛（N1–N8）与 N1 的「Java 必须始终可用」**。

### 4.1 三层结构（Java 保底 + 原生可插拔）

```
┌──────────────────────────────────────────────────────────────┐
│  业务层  pack/ glsl/ pipeline/ render/ screen/               │
│  —— 只依赖下面的接口，不知道背后是 Java 还是原生              │
└───────────────────────────┬──────────────────────────────────┘
                            │ 接口（纯 Java 类型）
┌───────────────────────────▼──────────────────────────────────┐
│  accel/  —— 加速层门面（Facade）                              │
│  interface GlslPassCompiler / PackScanner / OptionsFinalizer │
│  + 选择器：探测原生库可用性 → 选实现 → 打印所选后端            │
└──────────┬─────────────────────────────────┬─────────────────┘
           │                                 │
┌──────────▼──────────┐          ┌───────────▼─────────────────┐
│ backend-java/       │          │ backend-native/             │
│ 纯 Java 实现         │          │ FFM(FFI) → Rust cdylib      │
│ ✅ 永远存在          │          │ ⚠️ 可选，缺失则自动降级       │
│ ✅ 默认              │          │ ⚠️ 仅在 §5 实测通过后实现      │
└─────────────────────┘          └─────────────────────────────┘
```

**接口粒度规矩（决定 FFI 边界开销能不能被吃掉）**：

- 接口方法**只按"整批"设计**，不按"单条"设计。
  ✅ `int compileBatch(String[] sources, String[] options, ByteBuffer out)`
  ❌ `int compileOne(String line)`
- **不跨边界传 Java 对象**：传**大块连续内存**（`MemorySegment` / 直接 `ByteBuffer`）或字符串数组。
- **不跨边界抛异常**：返回错误码 + `thread_local` 错误信息缓冲，Java 侧转成异常。
- **不跨边界回调 Java**：如必须回调，用 `UpcallStub` 并显式管理生命周期，且回调内禁止 panic 外泄。

### 4.2 六条硬规矩

| # | 规矩 | 原因 |
|---|---|---|
| **N1** | **Java 实现必须始终存在且完整可用** | 原生库缺失 / 版本不匹配 / 平台不支持时，模组必须照常能跑 |
| **N2** | **原生库不得是启动的必要条件** | 不许因为找不到 `.dll` 就崩；降级必须打 WARN |
| **N3** | **同一进程内只用一种实现**（不逐调用切换） | 逐调用切换的边界开销会吃掉全部收益 |
| **N4** | **原生路径必须有 A/B 开关** | 否则无法判断问题是原生带来的还是别处坏的 |
| **N5** | 🔴 **`extern "C"` 函数体内必须 `catch_unwind(AssertUnwindSafe(…))`** | **Rust panic 穿过 FFI 边界 = UB → 直接 abort 掉整个 JVM**（游戏崩溃）。这是本项目最危险的原生坑，详见 §4.5 |
| **N6** | 🔴 **禁止 `panic = "abort"`**（`Cargo.toml` 的 `[profile.release]`） | 会让 N5 的 `catch_unwind` 完全失效，panic 必崩进程 |

### 4.3 语言与 FFI 选型

| 选项 | 何时选 | 代价 |
|---|---|---|
| **纯 Java**（含 `MemorySegment`、Vector API） | **默认**。先跑通、先测量 | 无跨平台构建负担；JIT 在热路径足够 |
| **Rust** | 冷路径转译吞吐、需无 GC 停顿、需现成解析 crate | 需 cargo + 交叉编译；`unsafe` FFI 边界要仔细 |
| **C++** | 需复用 glslang / SPIRV-Tools 等成熟 C++ 库 | 构建链最重；ABI 稳定性自负 |

#### FFM（Project Panama）vs JNI —— **本项目选 FFM**

Java 22 起 `java.lang.foreign` 正式（Foreign Function & Memory API），
Java 25 无需 `--enable-preview` 即可使用。

| | **FFM (Panama)** | JNI |
|---|---|---|
| 引入 | Java 22 正式 | 远古 |
| 是否需写 C 胶水 | ❌ 不需要 | ✅ 需要 |
| 绑定生成 | `jextract`（JDK 自带）从 C 头文件生成 | 手写 |
| 崩溃隔离 | `Linker` 有安全检查，缺符号在解析期报错 | 崩溃即整个 JVM 挂 |
| panic 边界 | 走 C ABI，同样需 N5 | 同样需 N5 |
| 调用开销 | 低（JIT 可优化） | 中（`RegisterNatives` 可优化） |
| 本项目适用性 | ✅ **选它** | ❌ 不选（胶水代码是额外维护负担） |

**标准接线流程**（每次新增原生模块都走这套）：

```
1. Rust 侧 crate-type = ["cdylib"]，产出 libvkdisp_accel.so / .dll / .dylib
2. cbindgen 生成 C 头文件
3. jextract 生成 Java 绑定（构建期，不入 jar）
4. 运行期：System.load(jar 内解压的路径) → SymbolLookup.loaderLookup() → linker.downcallHandle(...)
5. 缺符号 / 缺库 → catch 住 → WARN + 回落 backend-java（N2）
```

> **别被「native 一定快」误导**：跨 FFI 边界本身有固定开销。
> 只有当**一次调用内部的计算量 ≫ 边界开销**时，原生才有净收益。
> 这就是 §4.1「接口粒度要粗」的量化理由，也是 §5 阈值 20% 的来源。

### 4.4 候选模块与本轮选定范围

| 模块 | 分级 | 本轮是否实测 | 理由 |
|---|---|---|---|
| **`glsl/` 预处理 + 转译** | ❄️ 冷 | ✅ **是（本轮唯一对象）** | B3/B4 预算压力最大；串行、批量、纯计算 ⇒ FFI 粒度天然合适 |
| **`pack/` 解析（properties/options）** | ❄️ 冷 | ✅ **是（第二对象）** | 与转译串联，共用同一批输入 |
| `pipeline/` 管线键计算 | 🔥 热 | ❌ 本轮不测 | 先试 Java `Long.hashCode` 组合 / 预计算；超 B1/B2 再议 |
| `render/` uniform 装配 | 🔥 热 | ❌ 本轮不测 | FFI 每帧调用风险高，需先证明是瓶颈 |
| 着色器编译 | — | ❌ 禁止 | `07-CONSTRAINTS.md` T4；走原版通道 |
| Vulkan 设备 / 命令缓冲 | — | ❌ 禁止 | `07-CONSTRAINTS.md` T3 |

### 4.5 🔴 FFI 安全清单（每次写 `extern "C"` 逐条过）

```rust
// ✅ 正确姿势
#[unsafe(no_mangle)]
pub extern "C" fn vkdisp_compile_batch(
    src_ptr: *const u8, src_len: usize,
    out_ptr: *mut u8, out_cap: usize,
) -> i32 {
    // ① 必须 catch_unwind —— panic 穿 FFI = UB = 进程 abort
    let r = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        // ② 所有指针都必须校验，绝不 unwrap
        if src_ptr.is_null() || src_len == 0 { return ERR_INVALID_ARG; }
        let src = unsafe { std::slice::from_raw_parts(src_ptr, src_len) };
        // ③ 不要在边界里 panic-prone 的操作（索引越界、整数溢出、除零）
        compile_inner(src, out_ptr, out_cap)
    }));
    match r {
        Ok(code) => code,
        Err(_) => ERR_PANIC,          // ③ 兜底：转成错误码，绝不让 panic 外泄
    }
}
```

**必查项**：

- [ ] 每个 `extern "C"` 都有 `catch_unwind(AssertUnwindSafe(…))`
- [ ] `Cargo.toml` 的 `[profile.release]` **不是** `panic = "abort"`（N6）
- [ ] 每个裸指针都做了 null / 长度 / 容量校验
- [ ] 边界函数体内没有 `unwrap()` / `expect()` / 直接下标索引
- [ ] 没有跨边界抛 Java 异常（用错误码 + 错误信息缓冲）
- [ ] 没有跨边界回调 Java（若必须有，`UpcallStub` 生命周期显式管理）
- [ ] 内存归属明确：谁分配谁释放，Java 侧释放前 Rust 侧不再持有

## 5. 🔴 原生准入闸门（G 系列）：先实测，再决定做不做

> **本节是本轮的核心新增内容。** 旧版是「默认拒绝 + 六问」，
> 本版改为「**默认待测 + 闸门**」：允许写，但必须先过 G1–G4。

### 5.1 G 系列闸门流程

```
G0  取基准（Java 基线）
    └─ 分段计时：预处理 / 转译 / 解析 / 合计；预热 ≥3 次，取中位数；落盘 evidence/

G1  写等价 Rust 实现（仅本轮选定范围：glsl 预处理+转译、pack 解析）
    └─ 必须通过「输出一致性测试」：同一输入，Rust 与 Java 产物逐字节/逐 token 等价
       （不一致 ⇒ 谈不上性能对比，先修等价）

G2  写 FFM 最小打通 demo
    └─ Java → Rust → Java 单向；实测 FFM 边界单次开销（空函数调用）

G3  测性能并出对照表
    └─ 环境固定（机器/电源/JDK/包版本）；样本 ≥5；报中位数与 p95
    └─ 必须同时报：Rust 中位数、Java 中位数、比值、FFI 边界开销

G4  按阈值裁决（§5.2），裁决结论写回本节 + evidence/

G5  裁决为「采用」才进 §6（构建打包 + A/B 开关）；裁决为「不采用」登记结论后收工
```

### 5.2 裁决阈值（**先定，避免事后找理由**）

| 情形 | 裁决 |
|---|---|
| Rust 端到端中位数 **快 ≥ 20%**，且输出一致性测试全绿 | ✅ **采用**（进 §6） |
| 快 5%–20% | 🟡 **暂缓**：先在生产量最大的包上复测一轮；仍在此区间则**不采用**（收益会被维护成本吃掉） |
| 差异 < 5% | ❌ **不采用**：FFI 与构建链成本不划算 |
| Rust 慢 | ❌ **不采用**：记录数据，禁止反复尝试 |
| **输出一致性不通过** | ❌ **不采用**（无论多快）—— 两条实现不等价就没有可比性 |

> **20% 这个数字不是拍的**：它必须显著大于「跨语言构建链 + 四平台产物 + FFM 接线 +
> panic 边界防御 + 未来 ABI 维护」的持续成本。低于 20% 的收益无法覆盖这些成本。
