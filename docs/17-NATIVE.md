## 0. 一句话

**先找参考，再动手；先测出来，再优化；优化只做热路径，且必须能退回 Java。**

三条不可颠倒：**参考 → 测量 → 优化**。跳过前两步直接写 C++/Rust，是本项目最容易犯的错。

## 1. 纪律一：参考先行（动手前必须先查）

### 1.1 规矩

**任何一部分（解析器 / 转译器 / 编排 / GUI / 加速层）开工前，必须先做一轮参考调研。**
没有调研结论，不许动手写实现。

> 理由：本项目做的是「别人没做过的事」（OF 格式 → Vulkan），
> 但**每一块砖都有人做过**（预处理器、词法器、UBO 打包、帧图、管线缓存、FFI 桥）。
> 自己从零想，产出的一定比社区最成熟的实现差一个档次。

### 1.2 调研产出物（写进实现文件头部的注释块）

```java
// 【参考调研】<模块名>
// 1. 官方/主实现：<项目名 + 许可证> —— 参考了什么（做法 / 数据结构 / 边界条件）
// 2. 备选：<项目名 + 许可证> —— 为什么没选
// 3. 我们的差异点：<为什么不能直接用>
// 4. 许可证核对结论：<能不能并入本项目 MIT —— 默认不能，只读思路>
// 5. 性能基线：<同类实现的公开数据 / 自测数据>
```

**没有这个注释块 = 该模块未完成**（`07-CONSTRAINTS.md` T13）。

### 1.3 默认参考清单（按模块）

> ⚠️ **下表只用于「去哪找」，不代表可以直接抄。** 本项目 MIT，绝大多数参考项目是 GPL/LGPL，
> **只能读思路、读做法、读数据结构，不能搬代码**（`07-CONSTRAINTS.md` §〇 P1）。

| 模块 | 首选参考 | 许可证 | 能带走什么 |
|---|---|---|---|
| **GLSL 预处理器**（`#include`/`#define`/宏展开） | **IrisShaders/glsl-preprocessor** | ⚠️ GPL-3.0 + 例外条款 | 宏展开算法、行号映射、`#custom`/`#extension` 处理位置。**代码不可抄** |
| **GLSL 语法树 / 转译** | **IrisShaders/glsl-transformer** + 其 `licenses/` | ⚠️ 自定义（类 GPL 传染） | AST 节点设计与改写策略 |
| **OF 格式语义**（`shaders.properties` 等） | **Iris** 的 `shaderpack/parsing/` | LGPL-3.0 | **格式规范本身**（事实性信息，不受版权保护）+ 解析边界条件 |

| **帧图 / pass 编排** | Sulkan（GPL）/ Vitrail | GPL / LGPL | **往哪插入、用什么 API**（事实） |
| **管线 + mixin 挂载模式** | VulkanMod（LGPL） | LGPL-3.0 | 挂载模式的做法 |

## 2. 纪律二：性能预算（先定数字，再谈实现）

### 2.1 为什么必须先定

「兼顾性能」是形容词，不是验收标准。**没有数字，就无法判断优化有没有用、能不能停。**

### 2.2 预算表（本项目）

| 场景 | 目标 | 测量方式 | 优先级 |
|---|---|---|---|
| **不开包**（模组已加载但未启用） | 帧时间相对纯原版 **≤ +2%** | F3 屏 / Spark，同场景同视角 | **P0 必过** |
| **开包（中等包，如 BSL）** | 帧时间 **≤ 同机 Iris+OF 的 110%** | 同场景对比（`08-TESTING.md` §8） | P2 起 |
| **加载 / 切换包** | **≤ 3 秒**（中等包） | 计时日志 | P2 起 |
| **首帧编译**（进世界第一次） | 无 **> 200ms** 的单帧卡顿 | 帧时间直方图 | P3 起 |
| **内存** | 1 小时无持续增长；常驻增量 **≤ 200MB** | 任务管理器 / JFR | P1 起 |
| **解析阶段** | 中等包全部解析 + 转译 **≤ 1 秒** | 计时日志 | P2 起 |

> 「不开包 ≤ +2%」是本项目**最重要的性能指标**：
> 一个着色器模组最不能被接受的就是「不装包也掉帧」。

### 2.3 预算怎么用

```
① 实现一版（通常纯 Java，能跑通就行）
② 测 → 记录实测值
③ 超预算 → 定位到具体环节（§3 热度分级）
④ 只优化超预算的那个环节
⑤ 再测 → 达标即停，不要继续优化
```

**达标即停。** 优化到预算内还继续做，属于未经授权的范围扩大（`07-CONSTRAINTS.md` X12）。

## 3. 纪律三：热度分级（决定要不要上原生）

### 3.1 核心判断：**看调用频率，不看代码复杂度**

| 路径 | 触发时机 | 频率量级 | 允许的实现 | 能不能上原生 |
|---|---|---|---|---|
| 🔥 **热路径** | 每帧 / 每区块 / 每顶点 | 10³–10⁷ / 秒 | 极致：无分配、无装箱、无字符串拼、无反射 | ✅ 值得，但**先证明它真是瓶颈** |
| 🌤 **温路径** | 加载包、切维度、改选项、重载资源 | 几次 / 分钟 | 合理：可分配、可读优先 | ⚠️ 只有确实卡（> 预算）才考虑 |
| ❄️ **冷路径** | 首次解析 pack、选项 GUI 构建、首次编译 | **一次** | 清晰优先，性能无所谓 | ❌ **禁止**上原生 |

### 3.2 落到本项目的具体分级

| 环节 | 分级 | 说明 |
|---|---|---|
| 顶点属性拼装 / 格式转换 | 🔥 **热** | 每顶点一次 |
| uniform / UBO 写入 | 🔥 **热** | 每帧多次 |
| 管线缓存查找（hash 键构造） | 🔥 **热** | 每 draw 一次 |
| 矩阵运算 / 视锥剔除辅助 | 🔥 **热** | 每帧大量 |
| 纹理状态切换 / 描述符集绑定 | 🔥 **热** | 每 pass × 每资源 |
| **OF 包解析**（properties / gbuffers 扫描） | ❄️ **冷** | 加载时一次 |
| **GLSL 预处理器**（`#include` / `#define` 展开） | ❄️ **冷** | 加载时一次，结果进缓存 |
| **GLSL→M GLSL 转译** | ❄️ **冷** | 同上 |
| 选项 GUI 构建 | ❄️ **冷** | 打开时一次 |
| **管线首次编译** | ❄️ **冷** | 首次一次，之后走缓存 |
| **包切换 / 资源重载（F3+T）** | 🌤 **温** | 用户交互触发，需感知流畅 |

> ⚠️ **最容易踩的误区**：一看到「预处理器 / 解析器 / 编译器」就想到「这是 CPU 密集，写 Rust 吧」。
> **本项目这三样全是冷路径** —— 加载时跑一次，之后全走缓存。
> 把它们用 Rust 重写，**帧率提升为零**，却付出：跨平台构建链、四个平台的原生库、
> 反序列化边界、调试困难、许可证额外审查。
>
> 真正值得上原生的，只有 §3.2 上半张表（热路径），而且**必须先测出它确实是瓶颈**。

## 4. 原生加速的分层架构

### 4.1 三层结构（Java 保底 + 原生可插拔）

```
┌──────────────────────────────────────────────────────────────┐
│  业务层  pack/ glsl/ pipeline/ render/ screen/               │
│  —— 只依赖下面的「接口」，不知道背后是 Java 还是原生           │
└───────────────────────────┬──────────────────────────────────┘
                            │ 接口（纯 Java 类型）
┌───────────────────────────▼──────────────────────────────────┐
│  accel/  —— 加速层门面（Facade）                              │
│  interface VecMathOps / UboPacker / PipelineKeyHasher        │
│  + 选择器：探测原生库可用性 → 选实现 → 打印所选后端            │
└──────────┬─────────────────────────────────┬─────────────────┘
           │                                 │
┌──────────▼──────────┐          ┌───────────▼─────────────────┐
│ backend-java/       │          │ backend-native/             │
│ 纯 Java 实现         │          │ FFM(Panama) → C++/Rust 库    │
│ ✅ 永远存在          │          │ ⚠️ 可选，缺失则自动降级       │
│ ✅ 默认             │          │                              │
└─────────────────────┘          └─────────────────────────────┘
```

### 4.2 四条硬规矩

| # | 规矩 | 原因 |
|---|---|---|
| **N1** | **Java 实现必须始终存在且完整可用** | 原生库缺失 / 版本不匹配 / 平台不支持时，模组必须照常能跑 |
| **N2** | **原生库不得是启动的必要条件** | 不许因为找不到 `.dll` 就崩；降级必须打 WARN |
| **N3** | **同一进程内只用一种实现**（不逐调用切换） | 逐调用切换的边界开销会吃掉收益 |
| **N4** | **原生路径必须有 A/B 开关** | 否则无法判断问题是原生带来的还是别处坏的（同 `12-GAP-STRATEGY.md` §4 第 3 步） |

### 4.3 语言与 FFI 选择

| 选项 | 何时选 | 代价 |
|---|---|---|
| **纯 Java**（含 Vector API / `MemorySegment`） | **默认**。先跑通、先测量 | Java 25 的 Vector API 已能在热路径上接近原生（SIMD 友好） |
| **Rust** | 需要「无 GC 停顿 + 内存安全 + 现有成熟 crate」时 | 需 cargo + 交叉编译；`unsafe` FFI 边界要仔细 |
| **C++** | 需要复用现有 C++ 库（如 SPIRV-Tools / glslang）时 | 构建链最重；ABI 稳定性要自己保证 |

**FFI 手段首选 Panama（FFM API）**，不选 JNI：

| | Panama (FFM) | JNI |
|---|---|---|
| 引入于 | Java 22 正式 | 远古 |
| 是否需写 C 胶水 | ❌ 不需要 | ✅ 需要 |
| 崩溃隔离 | `Linker` 有安全检查 | 崩溃即整个 JVM 挂 |
| Java 25 状态 | **正式可用**（无需 `--enable-preview`） | 可用 |
| 调用开销 | 低（`Linker` 直接下到 `invokestatic`/`invokedynamic` 路径） | 中（但有 `RegisterNatives` 优化） |

> **别被「native 一定快」误导**：跨 FFI 边界本身有固定开销。
> 只有当**一次调用内部的计算量 ≫ 边界开销**时，原生才有净收益。
> 所以原生接口的粒度必须**粗**（一次调用处理一批数据），不能是「每顶点调一次」。

**边界设计规矩**：
- 传**大块连续内存**（`MemorySegment` / 直接 `ByteBuffer`），不传 Java 对象
- **不跨边界抛异常**：返回错误码 + 错误信息缓冲，Java 侧转成异常
- **不跨边界持有 Java 引用**（回调用 `UpcallStub` 并显式管理生命周期）
- 接口方法数**尽量少**（每多一个方法就多一处 ABI 契约）

### 4.4 候选模块（当前判断）

| 模块 | 当前判断 | 理由 |
|---|---|---|
| 顶点属性拼装 / UBO 打包 | 🟡 **候选**（先纯 Java，超预算再上） | 热路径，且天然「大块内存进、大块内存出」，适合 FFI |
| 管线缓存键计算 | 🟡 **候选** | 热路径；但先试 Java 的 `Long.hashCode` 组合 / 预计算 |
| 矩阵 / 视锥运算 | 🟡 **候选** | 热路径；先试 Vector API |
| 解析器 / 预处理器 / 转译器 | ❌ **不上原生** | **冷路径**，优化收益为零 |
| 着色器编译 | ❌ **禁止** | `07-CONSTRAINTS.md` T4；走原版通道 |
| Vulkan 设备 / 命令缓冲 | ❌ **禁止** | `07-CONSTRAINTS.md` T3；原版已完备 |

**结论：本项目大概率不需要原生库。** 但架构上预留（§4.1），
并且**只有在 §2 的测量证明某个热路径超预算时**才启用。

## 5. 决策树（要上原生之前，按顺序问）

```
Q1  这个模块在 §3 里是🔥热路径吗？
    ❌ 否 → 停。写清晰可读的 Java。（本项目解析器/预处理器/转译器都在这条路上）

Q2  它真的超 §2 的预算了吗？（有实测数据）
    ❌ 否 → 停。「感觉慢」不算证据。

Q3  能不能用纯 Java 手段解决？
    （缓存 / 预计算 / 避免分配 / Vector API / 换数据结构 / 降低调用频次）
    ✅ 能 → 先做这个，再测。

Q4  原生方案能带来 ≥ 20% 的净收益吗？（扣除 FFI 边界开销后）
    ❌ 否 → 不值得。收益会被维护成本吃掉。

Q5  四个平台的构建产物都搞得定吗？（Windows / Linux / macOS x64+arm64）
    ❌ 否 → 停。硬件兼容性比单点性能重要。

Q6  没有原生库时，Java 路径能独立跑对吗？（N1）
    ❌ 否 → 回去先补齐 Java 路径。

全部 ✅ → 才允许新增原生模块，并且必须：
        ① 登记进 §6 的本项目原生模块表
        ② 提供 A/B 开关（N4）
        ③ 保留 Java 实现（N1）
        ④ 加入构建产物校验（§6.3）
```

**默认答案永远是「不用原生」。** 上原生需要举证，不是默认选项。

## 7. 性能测量规范

### 7.1 每次性能相关改动都要有

```
[ ] 场景固定（同种子 / 同坐标 / 同视角 / 同渲染距离）
[ ] 三次运行取中位数（不是最好的一次）
[ ] 同时记录：F3 帧时间、各 pass 耗时、内存常驻
[ ] 对比基线：不开模组 / 开模组不开包 / 开模组开包
[ ] 原始数据落盘（不是只看一眼 F3）
```

### 7.2 常用手段

| 目的 | 手段 |
|---|---|
| 帧时间整体 | F3 调试屏（含 min/avg/max） |
| 定位是哪个环节慢 | 自己埋计时日志（`System.nanoTime()` 成对） |
| 采样式 CPU 剖析 | Spark profiler |
| GPU 侧 | RenderDoc / Nsight（Vulkan 后端下） |
| 分配 / GC | JFR（`-XX:StartFlightRecording`） |
| 冷路径（解析 / 转译） | 直接计时并打日志：`vkdisp: parse took {} ms` |
