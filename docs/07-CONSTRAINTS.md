## 〇·〇、三支柱总纲（2026-10-02 用户指令，最高优先级）

> 「目的依旧是**高性能，稳定，以及保持兼容性让 optfine/iris 着色器完整的运行在 vulkan 上**。」

本项目一切取舍按**三支柱优先级**裁决，冲突时按此顺序：

| 序 | 支柱 | 含义 | 硬性体现 |
|---|---|---|---|
| **1** | **兼容** | OptiFine/Iris 格式着色器**完整**跑在原版 Vulkan 上 | 功能覆盖优先于一切性能与优雅（X27） |
| **2** | **稳定** | 不崩、不闪、不静默降级、不泄漏 | 静默降级仍禁止（X11）；panic 边界新增 N5/N6（T17） |
| **3** | **高性能** | 帧时间贴近原版 + 切包等待可接受 | 预算 B1–B7（`17-NATIVE.md` §2.2），达标即停（X12） |

> 🔴 **优先级不是修辞，它决定具体条款怎么读**。例如：
> 「兼容优先」⇒ **允许为兼容而开 mixin**（M1 已松绑，见 §1.4）；
> 「稳定优先」⇒ **panic 跨 FFI 边界一律禁止**（T17/N5）；
> 「高性能但达标即停」⇒ **不许为了跑分而重构**（X12 继续有效）。

### 1.4 M1 的落地尺度（mixin 已松绑到「管线装配层」）

**背景（三轮演进，别读错旧结论）**：

| 版本 | 立场 | 结论依据 |
|---|---|---|
| 2026-09-29 ~ 10-02 早 | 零 mixin 是**默认路线**，从未成文为红线 | 保守推定 |
| 2026-10-02（P4.4 核实） | 源码级确认：零 mixin **做不到**完整 gbuffer 管线 —— ① `registerCustomPipelines` 用 `putIfAbsent`，改不了原版 location；② `SOLID_TERRAIN` 等写死 `ColorTargetState.DEFAULT`（单附件），派生管线要被地形用到必须走注入点；③ `BindGroupLayouts.Globals` 仅 9 字段，BSL 自定义 uniform 无处安放 | 硬证据 |
| **2026-10-02（本次）** | **用户拍板放开限制**：兼容完整 > 零 mixin | 三支柱优先级 |

**松绑后的规则（现行）**：

| 维度 | 允许 | 禁止 |
|---|---|---|
| **注入目标** | ✅ **管线装配层**：`ChunkSectionsToRender#renderLayers`（private，7 参，末两个是 `renderPipelineOverride`）、`RenderPipeline` 的构造/派生路径、帧图 pass 装配相关类 | ❌ 注入 Sodium / caffeinemc 任何类 |
| **注入目标** | ✅ 上述「装配层」内**必要的多个注入点**（不再限 1 个） | ❌ 注入 `RenderSystem` / `GlStateManager` / `GL11`/`GL14`/`GL15` 等底层状态类 |
| **注入目标** | ✅ 为让派生管线被地形/实体/天空 draw 用上，注入点可含 draw 调用侧 | ❌ 注入第三方区块渲染器（Vitrail 等） |
| **注入数量** | 🟡 **不设硬上限**，但每新增一个必须在本表登记（类名 + 方法 + 签名 + 用途 + 兼容性判定） | ❌ 未登记就注入 |
| **编码约束** | ① 目标类名/方法名只许引用 `bridge/MixinTargets` 常量；② `compatibilityLevel` 必须 `JAVA_25`（否则静默失效，见 X3）；③ 每个注入方法体**首行**打 `vkdisp: [注入点名] hit`；④ **只转发不写业务**（`06-MIGRATION` §2.2）；⑤ 每个注入点必须能**一键关闭**（配置项）以便二分定位 | ❌ mixin 类里写业务逻辑（升级时无法只改一处） |
| **稳定性要求** | 注入后若出现崩溃/validation error，**必须能通过关闭单个注入点定位** | ❌ 多个注入点互相耦合，无法单独关闭 |
| **默认策略** | **逐个开启**：先 1 个打通并验证，再考虑下一个 | ❌ 一次性全开 |

**为什么仍然禁止底层 GL 状态类**：那会绑死后端，违反 X7（OpenGL 环境直接崩），
且 VulkanMod 正是这条路 —— 本项目走 `renderpearl` 官方插口，不走后端替换。

**为什么不再限制「只 1 个」**：上一版把数量当红线，是因为当时认为零 mixin 路线能走通。
现在该路线已被证据否决，「1 个」的限制只会挡住兼容目标。**改为「登记制 + 可关闭制 + 逐个开启」，
把风险从「事前禁止」移到「事中可控 + 事后可定位」。**

**松绑后 mixin 解决得了的三件事（对照上一版「解决不了的三件事」）**：

1. ✅ **能覆盖原版管线的实际使用** —— 派生管线可被地形 draw 指向。
2. ✅ **能增附件** —— 派生管线改 `ColorTargetState` 即可上多附件 gbuffer。
3. ✅ **能加自定义 uniform 块** —— 派生管线自带 bind group 布局，顺带解掉 `Globals` 仅 9 字段限制。

### 1.2 L11 的落地尺度（Sodium 彻底隔绝）

**L11 是 L2 / L3 / L4 的加强版**，把「不抄、不替代、不提 PR」升级为**全链条隔绝**：

| 维度 | 要求 |
|---|---|
| 代码 | ❌ 不复制任何一行（L2 已覆盖） |
| 依赖 | ❌ 构建脚本里**不得出现**任何 `sodium` / `caffeinemc` 坐标（含 `compileOnly`） |
| 集成 | ❌ 不做运行时探测、不做「在场就用它」的分支、不引用其 API 包 |
| 兼容 | ❌ 不承诺与其共存可用，不为它做适配 |
| 命名 | ❌ 模组 id / 包名 / 类名 / 配置键里不出现 `sodium` 字样 |
| 文档 | ⚠️ 仅允许在**合规声明**语境下提及，且必须是**否定式**（"不与…做集成"）；不得出现任何**借鉴/复用/可选集成**式的正面表述 |
| 素材 | ❌ 不采用其 `mixin/sodium/*` 注入点、不读其内部类 |

### 1.3 L12 的落地尺度（调研时的合规核对）

**合规核对是调研的第 0 步，也是闸门**：许可证判不过 → **直接换参考，不再看它的代码**。

**正确顺序**（详见 `17-NATIVE.md` §1.1.1）：

```
第 0 步（闸门）  许可证是什么？能不能合法用在我的 MIT 工程里？
                ├─ 不能 → 放弃这个参考，换下一个候选（不要再读它的代码）
                └─ 能   → 继续
第 1 步          它怎么做的？
第 2 步          为什么这么做？
第 3 步          我们的差异点？
```

**为什么必须放第 0 步**：先读了代码再看许可证，就**无法自证**"实现没受影响"。
这是本项目（MIT）最容易被抓的把柄，也是最容易避免的 —— 只要顺序对。

**许可证判定表**：

| 参考的许可证 | 能否并入本项目 | 能带走 | 不能带走 |
|---|---|---|---|
| MIT / Apache-2.0 | ✅ 可以（保留署名） | 代码 + 思路 | — |
| LGPL-3.0 | ❌ 不可并入 | ✅ 思路、做法、事实 | ❌ 代码行 |
| GPL-3.0 | ❌ 传染 | ✅ 思路、做法、事实 | ❌ 代码行 |
| PolyForm Shield / 非竞争类 | ❌ 不可 | ⚠️ 连"借鉴"都谨慎（L11） | ❌ 代码，且不得集成 |
| All Rights Reserved | ❌ 完全不可 | ❌ 什么都别带走 | ❌ 全部 |
| **无 LICENSE 文件** | ⚠️ **默认 ARR**，视为不可用 | ❌ 什么都别带走 | ❌ 全部 |

**三个高频陷阱**：

1. **"GitHub 上能看见" ≠ "能用"**。无 LICENSE 文件 = 默认保留所有权利 = 跟 ARR 一样。
2. **"GPL + 例外条款"**（如 IrisShaders/glsl-preprocessor）—— 例外条款常只放开特定用途，
   **不等于对本项目放开**。此类**一律按禁止处理**，除非逐条读完并写进调研结论。
3. **平台页面与仓库文件冲突**（Modrinth 写 MIT、仓库里有 GPL）——
   **只信仓库的 `LICENSE` 文件**，并按**最严**的解释处理。

**查证顺序（按可信度）**：

1. 仓库根 `LICENSE` / `LICENSE.md` / `COPYING` ← **最权威，只信这个**
2. 源码文件头 SPDX 标识（`SPDX-License-Identifier:`）
3. ~~平台页面 License 栏~~ ← 常有错，仅作线索
4. ~~README 的 License 章节~~ ← 常有错，仅作线索

**拿不准时的默认动作**：**当作不能用**，只读思路。
宁可自己重写一个差一点的实现，也不并入来路存疑的代码。

> **产物要求**：【参考调研】注释块**第 0 条**写合规结论。
> 写「未核实」等同于没做调研 → 不许动手（`01-DEV-LOOP.md` §1 第 4 步）。

### 1.4 可以借鉴什么（判断标准）

**可以**：借鉴「往哪个方法注入」「该调用哪个 API」「该用哪个类」这类**事实性信息**——
不受版权保护，写进笔记、写进文档都可以。

**不可以**：复制「具体怎么写的代码」—— 一行都不落盘。

> ⚠️ **MIT 下的实操尺度**：由于不能再并入 LGPL 内容，判断要更保守。
> 拿不准的时候：**只用它告诉你的"该往哪打洞"，代码自己从零写。**

## 二、技术硬约束

| # | 约束 | 原因 |
|---|---|---|
| **T1** | **`mixins.json` 的 `compatibilityLevel` 必须为 `JAVA_25`** | 写 `JAVA_21` 在 Java 25 下**静默跳过全部 mixin**，不报错 |
| **T2** | **所有 GPU 操作必须走 `com.mojang.renderpearl.*`** | 用户约束：禁止重复造轮子 |
| **T3** | **不得自研 Vulkan 设备 / 命令缓冲 / render pass** | 官方有 |
| **T4** | **不得自研 SPIR-V 编译器** | 走原版编译通道 |
| **T5** | **业务代码不得直接 `import com.mojang.renderpearl.*`** | 必须经 `bridge` 包 —— 升级时只改一处（见 `06-MIGRATION.md` §2） |
| **T6** | **jar 内不得含游戏类**（`net/minecraft/**`、`com/mojang/**`） | 会与游戏冲突 |
| **T7** | **jar 内不得含任何第三方模组类**（`net/caffeinemc/**`、`dev/vitrail/**`） | 会冲突且牵连许可证 |
| **T8** | **`RenderTarget` / `TextureTarget` 仍在 `com.mojang.blaze3d.pipeline`** | 26.3 搬迁**不完整**，盲改包名会改坏 |
| **T9** | **顶点 stride 必须在绘制前断言一致** | 不匹配会画成彩色尖刺且无报错 |
| **T10** | **每一处 mixin 注入点必须打日志证明被调用** | 静默失败是本类工程的头号坑 |
| **T11** | **任何降级路径必须显式报错或打 WARN** | 不允许「失败得像没发生过」 |
| **T12** | **自制补充的特性必须收敛在 `platform/` 包，并登记在缺口表** | 官方更新后要能一处回退（见 `12-GAP-STRATEGY.md`） |
| **T13** | **任何模块开工前必须先做参考调研，未调研不许写实现**；且**调研的第 0 步是核许可证**（L12） | 社区每个子问题都有成熟解，从零想必然差一档；先读代码再看许可证则无法自证（见 `17-NATIVE.md` §1） |
| **T14** | **性能以 `17-NATIVE.md` §2.2 的预算表 B1–B7 为准；超预算的必须定位到具体环节** | 「兼顾性能」必须有数字，否则无法判断优化有没有用、能不能停 |
| **T15** | **原生库（C++/Rust）不得是启动的必要条件**（若将来真有原生库） | 找不到 `.dll` 就崩是不可接受的；Java 实现必须始终完整可用（`17-NATIVE.md` N1/N2） |
| **T16** | 🔴 **上原生之前必须走完 `17-NATIVE.md` §5 的 G 系列闸门**（G0 取基准 → G1 等价 Rust 实现 → G2 FFM 打通 → G3 测性能 → G4 按 20% 阈值裁决） | 2026-10-02 改写：原「禁止冷路径上原生」推理过度（冷路径影响切包等待 B3/B4，不是帧率）。改为**允许但强制实测**，禁止未测就上 |
| **T17** | 🔴 **`extern "C"` 函数体必须 `catch_unwind`；禁止 `panic = "abort"`** | Rust panic 穿过 FFI 边界是 UB，会直接 abort 掉整个 JVM ⇒ 游戏崩溃。**三支柱里「稳定」直接受此约束**（`17-NATIVE.md` N5/N6） |
| **T18** | 🔴 **原生接口粒度必须「按批」**（一次调用处理整批数据），不许「按条」调用 | 跨 FFI 有固定开销，逐条调用会把任何收益吃光（`17-NATIVE.md` §4.1） |
| **T19** | 🔴 **FFI 优先用 FFM（`java.lang.foreign`），不用 JNI** | Java 25 下 FFM 已正式，无需 C 胶水代码；JNI 的胶水是额外维护负担（`17-NATIVE.md` §4.3） |

## 三、编码规范

### 3.1 Java 风格

```java
// 缩进：4 空格，不用 tab
// 行宽：不超过 120 字符
// 嵌套：禁止超过 3 层，超出则提取方法
// this：字段与方法访问一律加 this.
```

### 3.2 空安全

```java
// 所有可空返回值必须标注（NeoForge 用 org.jspecify）
public @Nullable RenderPipeline compileProgram(ProgramStage stage) { ... }

// 禁止返回 null 表示「空集合」，用 Collections.emptyList()
```

### 3.3 资源管理

```java
// 所有 GPU 资源必须能释放，且释放是幂等的
@Override
public void close() {
    if (this.closed) return;
    this.closed = true;
    // ... 释放
}

// 用 try-with-resources 管理 RenderPass 等
try (RenderPass pass = this.openPass(descriptor)) {
    // ...
}
```

### 3.4 日志

```java
// 统一前缀 vkdisp:
private static final Logger LOGGER = LoggerFactory.getLogger("vkdisp");

// 热路径禁止字符串拼接（用参数化）
LOGGER.info("drawn {} sections", count);          // ✅
LOGGER.info("drawn " + count + " sections");      // ❌

// 每帧日志必须可关闭
if (DEBUG) { LOGGER.info("cull kept={}", kept); }
```

## 四、禁止事项（红线）

| # | 禁止 | 后果 |
|---|---|---|
| X1 | 用 `rm -rf` 之类清空目录 | 数据丢失 |
| X2 | 把任何第三方模组打进 jar | 类冲突 + 许可证牵连 |
| X3 | 在 mixins.json 用 `JAVA_21` | 静默失效，全部 mixin 不生效 |
| X4 | 在对外文字里写「替代 Sodium」 | 法律风险（且非事实） |
| X5 | 复制 Sodium / Sulkan / Beryl 的方法体 | 法律风险 |
| X6 | 向 Sodium 提 PR | 违反其贡献政策 |
| X7 | 硬编码假设后端一定是 Vulkan 而不做判定 | 在 OpenGL 环境崩 |
| X8 | 忽略 stride 校验 | 无声画面错误 |
| X9 | 「待确认项」用猜的值填 | 埋雷 |

## 五、依赖版本锁定

**唯一数据源：`gradle.properties`**（MDK 已如此组织）。

```properties
minecraft_version        = 26.3
minecraft_version_range  = [26.3,)
neo_version              = 26.3.0.41-beta
neo_version_range        = [26.3.0,)
mod_id                   = vkdisp
mod_group_id             = dev.vkdisp
```

**规则**：所有版本号只在这一处定义，其他地方引用变量。**禁止散落硬编码。**

**`neo_version` 与 `neo_version_range` 不可合并**（2026-10-03 确立）：

| 用途 | 用哪个 | 语义 |
|---|---|---|
| 编译期依赖（`build.gradle` → `neoForge.version`） | `neo_version` | 精确锁 `26.3.0.41-beta` |
| 运行时依赖声明（`neoforge.mods.toml` → `versionRange`） | `neo_version_range` | 只锁下限 `[26.3.0,)` |

理由：26.3 仍在 beta 期，官方每周发新版且版本号带 `-beta` 后缀。若把
`versionRange` 写成 `[26.3.0.41-beta,)`，用 41 之前任一 beta 的用户会被
**直接拒载**；等 26.3 转正，版号变成无后缀的 `26.3.0`，字符串不等，
不同加载器的版本序处理不一致，存在「明明装了却被判不满足」的风险。

> 本项目当前**没有发布到任何仓库**，这条约束是前瞻性的；但它同时是
> `build.gradle` 属性注入表里 `neo_version_range` 必须存在的原因 ——
> 模板里引用了它，少一个属性 `expand` 就会报错。

| 项 | 规则 |
|---|---|
| `.gitattributes` | 必须有 `* text=auto eol=lf`（Windows 下 `gradlew` 会被 CRLF 毁掉） |

| **禁止 trailer** | 🔴 **不得携带 `Co-Authored-By` / `Signed-off-by` / `Generated-with` 等任何 trailer**（2026-10-03 用户指令） |

### 6.1 禁止 AI 署名 trailer（2026-10-03 确立）

**规则**：本仓库的 commit message **不含任何 trailer**，尤其禁止
`Co-Authored-By: Claude ...`。

**为什么**：

1. **不是项目约定**。本节原本只规定了 `.gitattributes` / `core.autocrlf` /
   `gradlew` 可执行位 / 提交粒度 / 分支 / 提交前回归清单，**从未要求 trailer**。
   AI 工具按通用习惯自行添加，属于**没做上下文核实就动手**。
2. **版本号是编的**。`Claude Opus 4.5` 这类具体版本号，AI 并不该在 commit 里断言。
3. **仓库已有独立的署名习惯**。历史上带 trailer 的提交是**用户在 WSL 用 Claude
   开发时自己写的**，不是仓库规范要求的产物。AI 不得模仿或延续。

**边界**：本条只约束 **AI 代为执行的提交**。用户自己写的提交不受此约束，
用户想加什么都行。

**踩坑记录**：`691c75b fix(deps): versionRange 与 neo_version 解耦` 误带了
`Co-Authored-By: Claude Opus 4.5`。用户裁决「本次提交就这样，但之后不要再出现」
⇒ **不重写历史**（避免 force push 破坏已拉取的引用），仅立此规范。


> ⚠️ **实测坑**：clone 时若系统级 `core.autocrlf=true`，**工作区文件本身会落盘成 CRLF**，
> 光设 `.gitattributes` 不够 —— 必须实际 `sed -i 's/\r$//'` 重写一遍。
> 本工程已处理，新建仓库时照做。
