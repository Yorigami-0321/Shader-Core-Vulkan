# 12 · 原版 Vulkan 特性缺口与自行补充策略

> 本策略的授权来源：用户明确要求 ——
> 「**如果遇到 minecraft 原版的 vulkan 不支持的特性，可以自行补充，后续根据官方更新动态调整**」。
>
> 配套：`05-VERSION.md`（版本权威）、`06-MIGRATION.md`（升级流程）、`07-CONSTRAINTS.md`（T12）。

---

## 1. 策略一句话

**原版 Vulkan 后端是首选实现。当 OF/Iris 语义必需、而原版确实没有时，允许自行补充；
补充必须收敛、必须登记、必须能在官方补上之后一处回退。**

这不是"可以随便写 Vulkan 底层"的许可 —— 那仍然是 T3 的禁区。
自行补充的是**小的、可枚举的能力缺口**，不是重写驱动。

---

## 2. 判定顺序（必须先走完前四步，才轮到"自行补充"）

```
① 原版 api.* 里有没有？
     有 → 直接用。结束。
② 原版 backend.api.* 的 SPI 能不能表达？
     有（如 BackendRenderPipeline$CreateInfo 的字段）→ 用 SPI。结束。
③ 原版有没有"等价语义"的别的做法？
     有（换一个 pass 组织方式 / 换一种纹理用法达到同样效果）→ 改设计。结束。
④ OF/Iris 规范里这是"可选特性"吗？
     是（pack 声明为可选 / 有 fallback）→ 本期不实现，显式降级 + 打日志。结束。
⑤ 以上都不成立 → 走 §4 的自行补充流程。
```

**顺序不能颠倒。** 先想到"自己写"就跳到最后一步，是本项目最容易犯的错。

---

## 3. 什么算"可以自行补充"

### 3.1 允许（典型形态）

| 形态 | 例子 |
|---|---|
| **原版已暴露但未接线** | 原版 `VulkanFeature` 枚举里有某能力，但默认 feature set 没开；本项目在自己的设备创建路径里补上 |
| **薄封装** | OF 语义需要一个 `Sampler` 组合（如比较采样器 + 自定义寻址），原版有原件但没现成组合 |
| **格式/布局映射表** | GL 枚举 ↔ `VkFormat` 的映射表（OF 包大量依赖 GL 风格格式名） |
| **资源生命周期管理** | `colortex0..15` / `depthtex0..2` / `shadowtex0..1` 这一整套命名目标的池化与复用 |
| **多级联/多目标的编排** | OF 的 shadow 多级联在原版帧图里没有直接对应物，需要自行组织 pass 序列 |

### 3.2 不允许（越界）

| 越界 | 为什么 |
|---|---|
| 自己实现 Vulkan 设备 / 队列 / 命令缓冲 / 交换链 | T3 禁区，且原版已完备 |
| 自己实现 GLSL→SPIR-V 编译器 | T4 禁区；且与本项目主线无关 |
| 绕过原版 `GpuDevice` 直接拿 `VkDevice` 干活 | 破坏原版的资源跟踪与生命周期，必然踩同步 bug |
| 引入任何第三方渲染模组/着色器加载器的服务端或第三方库 | 违背"独立实现"+ 许可证风险（`07-CONSTRAINTS.md` L11） |
| 为了让某个 pack 跑起来而改原版类的行为 | 会影响其他模组，且升级即失效 |

## 4. 自行补充的流程（五步，缺一不可）

### 第 1 步 先记录缺口，再写代码

在 `docs/13-GAP-REGISTRY.md` 新增一行。**没有登记就不许写实现。**

| 字段 | 说明 |
|---|---|
| 缺口 ID | `GAP-001` 递增 |
| 需求来源 | 哪个 pack / 哪条 OF 语义 / 哪个 stage |
| 原版现状 | 为什么 §2 的①~④ 都不成立（要写清"查过了" ） |
| 补充方案 | 打算怎么做 |
| 影响面 | 涉及哪些类、是否需要 mixin |
| 回退条件 | 官方补上什么之后可以删掉这份补充 |

### 第 2 步 全部落在 `platform/` 包

```
dev/vkdisp/platform/
    └── 所有"原版没有、我们自己补"的东西只放这里
```

**硬要求**
- 业务包（`pack/` `glsl/` `pipeline/` `render/` `screen/`）**不得** import `platform/` 之外的实现细节
- 业务包只调 `platform/` 暴露的接口 —— 这样官方补上之后，把 `platform/` 的实现换成原版调用即可
- 每一处补充的代码头部必须写明：

```java
// 【自行补充】GAP-003
// 原版现状：<原版为什么做不到>
// 官方补上后可移除：<判定条件>
// 登记：docs/13-GAP-REGISTRY.md
```

### 第 3 步 必须有可关闭开关

每一项自行补充都要有独立开关（配置项或常量），**默认可以是开**，但必须能一键关掉。
目的：验证"这是补充带来的"还是"别处坏了"。

### 第 4 步 必须有诊断日志

补充路径必须打日志，说明**它被走到了**。

```java
LOGGER.info("vkdisp: [GAP-003] using self-supplemented path, reason={}", reason);
```

> 没有这条日志，将来官方补上之后你无法知道哪条分支还在被使用。

### 第 5 步 登记表收尾

把"实际实现方式"与"验证结果"回填进 `13-GAP-REGISTRY.md`。

---

## 5. 动态调整流程（官方每次更新后执行）

这步并入 `06-MIGRATION.md` §4 的升级流程，作为**第 4.5 步**：

1. 升级版本号 → 编译 → 收集符号缺失错误
2. **复查缺口登记表**：逐行问「原版这次补上了吗？」
   - 补上了 → 打开该补充的开关做 A/B，确认行为一致后**删除补充实现**，改为调用原版
   - 没补上 → 检查原版 API 是否变了导致补充实现需要跟着改
   - 原版**移除**了补充所依赖的东西 → 立即停止升级、回滚（同 `06-MIGRATION.md` §7 止损）
3. 把本次复查结论写入登记表的"官方更新复查记录"段

**复查不是可选项**：官方更新后不看登记表，会导致"补充实现"永久沉积，
最后没人知道哪些代码是必要的、哪些是历史包袱。

---

## 6. 判定"该不该自行补充"的三问

动手前自问，任一为「是」就不该自己做：

1. **这个能力是不是"整个 Vulkan 后端"级别的？** → 是则不做（T3）
2. **这个能力是不是"着色器编译"级别的？** → 是则不做（T4）
3. **有没有更简单的等价设计能达到同样画面？** → 有则改设计，不补

## 8. 与「原生加速」（`17-NATIVE.md`）的区别（别混）

这两件事看起来像、实际完全不同，**不要用一个决策代替另一个**：

| | 本文（特性缺口） | `17-NATIVE.md`（性能） |
|---|---|---|
| 触发 | OF/Iris 语义必需，原版**没有**该能力 | 某环节**超性能预算** |
| 解决手段 | 在 `platform/` 补实现（**仍然是走原版 API**） | 换语言（Java → C++/Rust）+ FFI |
| 判定顺序 | §2 的 ①→⑤ | §5 的 Q1→Q6 |
| 共同点 | **都必须先登记、必须有开关、必须有日志、都必须能回退** | 同左 |
| 常见误用 | 拿「性能」当理由去写底层 Vulkan（❌ T3 禁区） | 拿「原版没有」当理由去写原生（❌ 先走本文 §2 的四步） |

**一句话**：本节管「缺什么能力」，`17-NATIVE.md` 管「够不够快」。**缺能力 ≠ 需要换语言。**
