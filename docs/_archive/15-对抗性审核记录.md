> 三方独立质询（产品 / 架构 / 风控）+ 分歧裁决。
> 本项目涉及许可合规风险，故启用完整版审核。

## 一、审核对象

- 主计划：`Shader-Core-Vulkan-开发计划.md`
- 文档包：`Shader-Core-Vulkan-docs/`

## 二、三方结论摘要

| 视角 | 结论 | 关键意见 |
|---|---|---|
| **产品设计师**（需求真不真） | ✅ 需求真实 | 「让存量 pack 在 Vulkan 上跑」是真实且明确的痛点，Vitrail 已经在做这件事，本项目是其必要组件 |
| **架构师**（技术可行性） | ⚠️ 可行但有前提 | 路线 A 技术可行但合规有问题；路线 C 需要上游配合，**不能单方面推进** |
| **风控师**（合规安全） | 🔴 **一票否决路线 A** | PolyForm Shield Noncompete 明确禁止竞争产品；「假 Sodium」是最典型形态 |

**裁决**：按技能的方法论，决策优先级为 **安全合规 > 落地可行性 > 用户价值 > 实现成本**。

→ **风控意见覆盖架构意见**：技术可行不等于可以开工。**推荐路线 C。**

## 三、产品设计师质询

**Q1：这个项目服务的对象是谁？**
A：Vitrail-Shaders 的用户——即「想让存量 OptiFine 格式 pack 在 Minecraft 自带 Vulkan 渲染器上运行」的玩家。

**Q2：不做这个项目会怎样？**
A：Vitrail 目前依赖 Sodium。若 Sodium 在 26.3 Vulkan 上的支持不理想（或玩家不想装 Sodium），这些用户就没有可用路径。

**Q3：Vitrail 自己不能解决吗？**
A：Vitrail 是着色器引擎（GLSL→SPIRV），不做区块网格化与剔除。这部分必须有渲染后端提供。

**Q4：为什么必须是「我们」做？**
A：不一定。但只有我们明确在做。若走路线 C，还需要说服 Vitrail 上游接受后端抽象——**这是最大的不确定性**。

**产品结论**：需求真实，但**成功不取决于我们写得多好，而取决于上游是否配合**。

## 四、架构师质询

**Q1：Vitrail 需要 Sodium 的哪些部分？**
A：58 个类型，其中 **37 个在 `client/` 内部**（含 10 个 mixin 注入点），21 个在公开 `api/`。

**Q2：能不能只用公开 api 包？**
A：**不能。** Vitrail 的 10 个注入目标 100% 在 `client/` 内部，公开 api 包只提供 `blockentity/config/internal/math/memory/texture/util/vertex`。这是路线 B 走不通的根本原因。

**Q3：如果不用 Sodium 的 FQN，Vitrail 能工作吗？**
A：**不能直接工作。** Vitrail 的 `@Mixin(value = DefaultChunkRenderer.class)` 会找不到目标。必须改 Vitrail。

**Q4：改 Vitrail 的代价有多大？**
A：需要把 `dev.vitrail.sodium.*`（8 个类）与 `dev.vitrail.mixin.sodium.*`（8 个 mixin）+ `dev.vitrail.mixin.access` 里的 2 个 accessor，抽象为一个后端接口。工作量中等，且**必须上游同意**（因为要改 Vitrail 的架构）。

**Q5：有没有第三条路？**
A：有，但都有代价：
- 让 Vitrail 上游自己做（等于本项目不存在）
- 等 Sodium 官方提供后端接口（Sodium 无此计划）
- 走路线 A 并拿到授权

**架构结论**：**路线 C 是唯一技术上干净且合规的路径，但它把成功的关键交给了上游。**

## 五、风控师质询

**Q1：Sodium 是什么许可证？**
A：**PolyForm Shield 1.0.0**（非 GPL）。关键条款是 **Noncompete**。

**Q2：「假 Sodium」是否违反 Noncompete？**
A：**很可能违反。** 原文：「Any purpose is a permitted purpose, **except for providing any product that competes with the software**」，且 Competition 条款明确：「**If you market a product as a practical substitute** for the software…, it definitely competes.」

用 `modId="sodium"` 顶替其作为前置，是「practical substitute」的最典型形态。

**Q3：复刻包名 `net.caffeinemc.mods.sodium.*` 有问题吗？**
A：有问题。它同时制造「同一产品」的观感，并属于对 Sodium 的实质借用。

**Q4：只参考签名、不抄代码，可以吗？**
A：签名偏事实信息，风险较低，但**批量复刻 37 个内部类的结构**可能被认定为衍生作品。且 PolyForm 的 Changes 条款把衍生限制在「permitted purpose」内——竞争不是 permitted purpose。

**Q5：有没有先例？**
A：有。Sodium 在 Modrinth 上公开声明：「Not compatible with any version of 'Sodium Options API', which is not affiliated with us, and any mods that depend on it.」——**第三方擅自做的 Sodium 兼容层被官方公开切割是有先例的。**

**Q6：如果拿不到授权，路径是什么？**
A：路线 C——不冒充、不复刻 FQN、不营销为替代品。做一个独立的「Vitrail Vulkan 后端」。

**Q7：还有别的合规陷阱吗？**
A：有两条：
1. **不要向 Sodium 提 PR**——其 CONTRIBUTING 明确「We will not accept pull requests which contain *any amount* of AI-generated code」。
2. **分发含 Sodium 制品必须附 PolyForm 全文或 URL**（Distribution 条款）。

**风控结论**：🔴 **路线 A 一票否决**（除非取得书面授权）。路线 C 合规。

## 六、分歧与裁决

### 分歧 1：路线选择

| 方 | 主张 |
|---|---|
| 产品 | 想让项目尽快落地，路线 A 最快 |
| 架构 | 路线 A 技术最直接；路线 C 依赖上游 |
| 风控 | **路线 A 法律风险不可接受** |

**裁决**：**安全合规 > 落地可行性** → 采用**路线 C**，并把「向 Vitrail 上游提案」列为 Phase 0 的第一步。

### 分歧 2：是否现在就动工

| 方 | 主张 |
|---|---|
| 产品 | 先做技术验证，法律问题后议 |
| 风控 | 法律问题必须先议，否则做出来也不能发 |

**裁决**：**先做 Phase 0 的「上游提案」与「授权咨询」**，两者任一有结果再进技术阶段。
