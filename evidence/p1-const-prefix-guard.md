# P1 · Java 侧「先挡后正则」前缀守卫 —— 实测只省 4.9%，假设被证伪

> 对应 `17-NATIVE.md` §7.4 结论里的 **P1**：「实测 Java 侧『先挡后正则』能把 const 的
> 243.9ms 砍掉多少」。**答案：12.0ms / 4.9%。**
>
> 本轮**最有价值的产出不是那 4.9%**，而是**证伪了「const 的 244ms 是正则主导」这个假设**，
> 并给出了真实的热区分布 —— 后者决定了下一步该往哪投入。

## 环境

| 项 | 值 |
|---|---|
| 机器 | AMD Ryzen 7 8745H / Linux amd64 / WSL2 |
| Java | JDK 25.0.4.1（`vkdisp` 本仓库） |
| 输入 | BSL_v10.1.8，182 阶段，共 **311,902 行** / 17,298,868 字节（inc 产物） |
| 协议 | **同一二进制内 A/B**（`-Dvkdisp.const.guard=true/false`）交替 9 轮，每轮预热 3、样本 9 |

## 改了什么

`ConstEvaluator.evaluate` 原本对**每一行**无条件做：`line.strip()` →
`originOf()` → `CONST_PATTERN` → `DEFINE_PATTERN`。

优化加了一层前缀守卫：只有 `trimmed.startsWith("const") || startsWith("#define")`
的行才进正则与 `originOf`。

**可证明等价**：两条 pattern 都带 `^` 锚定（`^const\s+…` / `^#define\s+…`），
所以不满足前缀的行**必然失配**，跳过不丢任何匹配。
`originOf` 越界返回 `UNKNOWN_LINE`、**永不抛**（`SourceLineMap` 契约），
因此把它推迟到命中之后也不改变异常语义。

## 等价性判据（X27：不许为性能砍 pack 特性）

const 相的产物**不含文本**，所以等价性只能靠「选项 + 诊断全量清单」来证：

```bash
java -Dvkdisp.const.guard=false -cp … ColdPathBenchmark --dump-const /tmp/ab/off
java -Dvkdisp.const.guard=true  -cp … ColdPathBenchmark --dump-const /tmp/ab/on
sha256sum /tmp/ab/off/*/const-results.txt /tmp/ab/on/*/const-results.txt
```

| 项 | 关闭（原行为） | 开启（优化后） |
|---|---|---|
| 选项常量条数 | **51,336** | **51,336** |
| 诊断条数 | **0** | **0** |
| 清单 sha256 | `1c7cfedde4119d61c…` | `1c7cfedde4119d61c…` |

**✅ A/B 产物逐字节完全一致。**

另外补了 4 条单测钉住守卫最容易被人改坏的边界：
行内含关键字但**行首没有**（若守卫写成 `contains` 就会误认）、strip 后仍应放行、
前缀相符但语法不符应正常失配、冲突禁用 + WARN 路径必须照旧走到。
测试数 **607 → 612**。

## 🔴 假设被证伪：const 的 244ms 不是正则主导

先用一个**独立探针**在同一批数据上量各个成分：

| 成分 | 耗时 |
|---|---|
| 全部行跑两条正则 | **29.6 ms** |
| 只做前缀判断 | 11.3 ms |
| 只做 split + strip | 11.1 ms |

⇒ 两条正则加起来只有 **~18ms**。Java 正则在失配时本来就很便宜
（`^const` / `^#define` 是字面量前缀，引擎有前缀优化），
所以「先挡后正则」能省的本来就不多 —— **我的假设一开始就错了**。

再用 JFR 采样（`settings=profile`，const 相 128 个采样，与顺序无关的归因）：

| 归因 | 占比 |
|---|---:|
| **evaluate 自身的循环 / 内联** | **37.5%** |
| **`strip`** | **18.0%** |
| **`split`** | **17.2%** |
| `tryDefineOption` | 16.4% |
| `tryConst` | 10.2% |
| `parseCandidates` | 3.9% |
| `originOf` | 0.8% |

**真正的热区是「把 17MB 文本切成一堆行、每行再 strip 一遍」这类字符串分配，
合计约 35%**；正则入口约 27%，其余是循环自身的簿记。

## 对决策的影响

| 观察 | 含义 |
|---|---|
| Java 侧「小修」最多只能拿到 4.9% | 「用一次廉价前置判断替掉 const 的 Rust 移植」这条**便宜路径基本走不通** |
| 35% 在 split/strip 的分配 | 真要动就得**结构性改写**（单遍扫描、只对可能命中的行 strip），不是加守卫 |
| Rust 在 inc 上的 4× 优势来自「跳过正则」 | 而 const 的正则**本来就不贵** ⇒ **Rust 在 const 上未必能复制 inc 的优势** |

⇒ §7.4 三种假设里，**假设 B（const 按 inc 的 4.01× 移植 → 快 54%）现在明显偏乐观**；
更现实的区间接近假设 C。**const 的归属仍未决，但天平已经偏向「不值得为它上 Rust」。**

## 🔴 本文件**没有**证明的事

| 未覆盖 | 说明 |
|---|---|
| **不是 const 的最终优化方案** | 守卫只省 4.9%；结构性改写（单遍扫描）未做、未测 |
| **只有 BSL** | 别的包行数与选项密度不同，比值会变 |
| **JFR 归因是采样** | 128 个采样足够看量级，不足以做微基准级别的精确归因 |
| **没有验证「Rust 移植 const 会更慢」** | 上面只是**推断**（正则不贵 ⇒ Rust 的优势来源不存在），不是实测 |
| **没有改动 G0 的四段口径** | `--phase-timing` 是另起一趟，G0 历史数字继续可比 |
| **const 跨轮极差 11% 未解释** | 优化前后都是 ~11%，比 inc/def 的 1.4–2.8% 高一个量级，本轮仍未定位 |

## 结论

1. ✅ 前缀守卫**已落地**：4.9% 收益、**A/B 产物逐字节一致**、4 条边界单测、留了开关可交替测量。
2. 🔴 **「const 是正则瓶颈」的假设被证伪**；真实热区是字符串分配（split/strip ~35%）。
3. ⇒ 「便宜路径」基本走不通；**const 移植与否仍需裁决，但天平已偏向「不值得为它上 Rust」**。
   下一步若要动 const，应做**结构性改写并单独取证**，而不是继续找廉价前置判断。
