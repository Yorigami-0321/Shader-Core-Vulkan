# PP · 解析段 profile —— 发现生产路径把预处理算了两遍，修复后冷路径快 39.3%

> 对应上一轮定下的 **PP（profile parse）**：G0 四段里 `properties/options 解析` 占 43%
> （约 681ms），是最大的单块却从未被 profile。
>
> **本轮的两个产出**：
> ① **G0 的四段口径本身有误** —— 「解析」段并不是纯解析，它**重复计算了预处理**；
> ② 顺着这个线索发现并修复了**生产路径的真实缺陷**：同一批文件的预处理被算了两遍。
> 修复后生产入口 **1458.5 → 885.0ms（快 39.3%）**，产物 **182/182 阶段逐字节一致**。

## 环境

| 项 | 值 |
|---|---|
| 机器 | AMD Ryzen 7 8745H / Linux amd64 / WSL2 |
| Java | JDK 25.0.4.1 |
| 输入 | BSL_v10.1.8，182 阶段 |
| 协议 | 同一二进制 A/B（`-Dvkdisp.reuse.preprocess=true/false`）**交替 9 轮**，预热 3、样本 9 |

## ① G0 的四段口径有问题：解析段在重复计算

JFR 采样「含 `ShaderPackService.load`」的栈（167 个采样），栈顶归属：

| 栈顶 | 占比 | 属于 |
|---|---:|---|
| `assembleOptions` | 19.2% | **真的**选项解析 |
| `screenOf` | 14.4% | **真的**选项解析 |
| `DefineProcessor.process` | 12.0% | ⚠️ **预处理** |
| `GlslDeclarationExtractor.stripComments` | 9.0% | 声明提取 |
| `DefineProcessor.emitting` | 9.0% | ⚠️ **预处理** |
| `SourceLineMap$Builder.build` | 7.2% | ⚠️ 预处理产物 |
| `ConstEvaluator.evaluateSinglePass` | 5.4% | ⚠️ **预处理** |
| `IncludeProcessor.process` / `expandMacros` | 6.0% | ⚠️ **预处理** |
| 其余（`load` 自身 / `collectSource` / `Program.<init>`） | ~18% | 组装 |

🔴 **约 48% 的「解析」段其实是预处理与声明提取。**

根因：`ShaderPackService.load` 为了提取 uniform / 顶点属性，对每个 program 的两个阶段
各跑一次**完整的 `GlslPreprocessor.analyze`**（include + define + const 三段全走），
而 G0 的「`#include` 预处理」段量的是同一件事 —— **四段合计把预处理算了两遍**。

⇒ **上一轮据「解析占 43%」把工作重心从 const 移开，方向建立在被高估的那一块上。**
这是本轮最该记住的教训：**分段数字在被使用之前，先确认它量的确实是它自称的东西。**

## ② 顺着线索发现的真实缺陷：生产路径预处理算两遍

顺着 `load` 内部那次预处理往下看，发现**它不止影响基准，生产代码也中招**：

```
ShaderPackCompiler.compile(discovered)
  └─ ShaderPackService.load(discovered)          ← ① 为提取声明，对 182 个文件跑一遍完整预处理
  └─ compileStage(...) × 182
       └─ GlslPipeline.run(stage, …)             ← ② 为真正转译，对同一批文件又跑一遍
```

同一个文件、同一个 resolver、同一份输入 —— **纯重复**。

（`compile` 里已有注释承认「`load` 内部已 plan 过一次」，说明重复这件事被知道，
只是当时只想到 `MountPlan`，没往预处理上想。）

## 修复

| 文件 | 改动 |
|---|---|
| `GlslPipeline` | 新增 `runPreprocessed(stage, preProcessed)`；`analyze` 的后半段**改为调用它** |
| `ShaderPackService` | `load` 增加重载，回填「源文件路径 → 预处理产物」sink |
| `ShaderPackCompiler` | 无选项覆盖时建 sink，`compileStage` 命中则走 `runPreprocessed` |

**收敛点纪律**：`analyze` 的后半段直接委托给 `runPreprocessed`，两条路径**共用同一段
诊断合并代码**，而不是各写一份 —— 从结构上排除逻辑分叉的可能。

**只在无选项覆盖时复用**：有覆盖时 `compileStage` 用的是**改写过的 resolver**，
两次预处理本就不同，必须各算一次。这条判断写在代码注释里，不是隐含约定。

开关 `-Dvkdisp.reuse.preprocess=false` 保留：既是 §7.3 红线要求的交替测量手段，
也是怀疑等价性时一条命令退回原路径的保险。

## 数据：生产入口冷路径快 39.3%

| 实现 | 中位数 | p95 | min | max | 跨轮极差 |
|---|---:|---:|---:|---:|---:|
| 原路径（预处理算两遍） | **1458.5 ms** | 1613.8 | 1377.6 | 1653.0 | 18.9% |
| 复用 load 的预处理 | **885.0 ms** | 989.6 | 817.2 | 1050.7 | 26.4% |

**快 573.5ms / 39.3% / 1.65×** —— 纯 Java，无 FFI、无四平台产物、无 panic 边界。

> ⚠️ 跨轮极差 18.9%–26.4% 明显偏大：生产入口一趟含 zip I/O 与整轮 GC，
> 抖动天然比纯计算段大。**但效应量 39.3% 远大于噪声**，且两侧交替、样本 ≥9，
> 结论成立。§7.1 要求报 p95，故一并给出。

## 对决策的影响

这是目前找到的**最大的杠杆**，而且它推翻了几个此前的判断：

| 此前判断 | 修正 |
|---|---|
| 「解析占 43%，是最大单块」 | 🔴 **被高估**：其中约 48% 是重复计算的预处理 |
| 「优化 const 更划算，因为它是预处理里最大的一块」 | ⚠️ const（227.6ms）仍存在，但它在**生产入口**里只占 ~16%（885ms 里约 227ms） |
| 「要不要上 Rust，得先等 const 的结论」 | 🔴 **在问错问题**：真正的浪费不在语言层，而在**同一份工作被算了两遍** |

⇒ **支柱③高性能（B3/B4）的第一优先级不是换语言，是消除重复计算。**
Rust 那条线的价值需要在这个新基线上**重新评估** —— 因为基线已经变了：
此前 G1 的 Rust 数据是拿「含重复计算的 1458ms」比出来的，**分母不对**。

## 🔴 本文件**没有**证明的事

| 未覆盖 | 说明 |
|---|---|
| **G0 的四段表尚未修正** | 本轮只修生产代码；`ColdPathBenchmark.runPass` 的分段仍把 `load` 当「纯解析」量，**口径仍需修**（已登记为下一轮入口） |
| **没有 runClient 取证** | 本轮全部是离线基准；生产入口的收益**尚未在客户端里验证**（§5.1 R2–R7） |
| **只有 BSL / 只有冷路径** | 帧时间不受影响（`17-NATIVE` §0 已明确） |
| **跨轮极差 26.4% 未解释** | 疑与整轮 GC / zip I/O 有关，未取证 |
| **`PackCompileCache` 的交互未验** | 切包路径本来就缓存，复用是否与之叠加未测 |
| **选项覆盖路径未测** | 复用只在无覆盖时生效；有覆盖的路径行为**未改动也未取证** |

## 结论

1. 🔴 **G0 四段口径有误**：「解析」段约 48% 是重复的预处理。上一轮据此调方向是错的。
2. ✅ **生产路径确实把预处理算了两遍**，已修复。
3. ✅ 生产入口 **1458.5 → 885.0ms（快 39.3%）**，产物 **182/182 逐字节一致**，616 单测全绿。
4. ⏭️ **G 线需要在新的基线上重估** —— 之前的 Rust 对照分母含重复计算。
