# G2 补充 · 回传方向实测 —— Rust → Java

> 补上 G2 **最后一个没被量过的方向**。此前测的都是 **Java → Rust 单向**（把源码传进去），
> 按批下跨界成本可忽略（5.917ms 里跨界机制只占 0.009ms）。
> 但**预处理产物本来就是要回传的** —— Rust 处理完要把结果交回 Java，
> **方向相反、载荷同样大**，而这个方向一次都没量过。

**实测已完成**（两次独立运行，结论一致）。测量前机器已确认空闲：
`/proc/loadavg` 0.12–0.75，无高 CPU 进程、无残留游戏进程。

## 结论先行

### ✅ 现在就可以定的一条（**不依赖性能数字**）

> 🔖 **「C（写进 Java 分配的堆外缓冲）是唯一没有所有权陷阱的形态」——
> 这一条不需要等实测就已经成立，可以现在就写进设计结论。**

理由与实测无关，纯属所有权语义：

| | 所有权风险 | 泄漏风险 | 并发 |
|---|---|---|---|
| A 回传指针 | 🔴 **高**（跨调用即 use-after-free） | 无 | 🔴 **不支持**（全局静态） |
| B 拷贝 | 低 | 🔴 **高**（漏 `free_buffer` 就漏一块载荷大小） | 支持 |
| C 写进 Java 缓冲 | **无** | **无** | 支持 |

**A 与 B 各带一个「做对了没事、做错了就出事」的坑**：
A 的坑是「结果没在下次调用前用完」，B 的坑是「漏了成对的 `free_buffer`」。
而 §5 的三支柱里「稳定」排在「高性能」前面 ——
所以**只要实测显示三者耗时差异不大，就应当直接选 C**。

> 这是 §5.2「20% 阈值必须显著大于持续成本」那条思路在**单个接口设计点**上的应用：
> 宁可少拿一点吞吐，也要把「写错就出事」的那类风险拿掉。
> 🔴 但这句话的前提是「差异不大」——**差异到底多大仍待实测**，
> 若实测显示 A 显著更快，那就要重新权衡，不能无脑选 C。

### ✅ 实测结论：**35.7% → 35.5%**

**回传加上之后只掉 0.2 个百分点。** 整包回传开销：

| 形态 | 每字节斜率 | 整包（550 次跨界） | 端到端 |
|---|---:|---:|---:|
| A 回传指针 | 0.0231 ns | **1.207 ms** | **35.5%** |
| B 拷贝 | 0.0230 ns | **1.201 ms** | **35.5%** |
| **C 写进 Java 缓冲** | 0.0226 ns | **1.183 ms** | **35.5%** |

（上一轮只算 Java→Rust **传入**，整包 5.917 ms，对应 35.7%。）

> 🔖 **而 A / B / C 三者的耗时在所有真实载荷档（≥1KB）上都在噪声内不可区分**
> —— 64B 档 B 略高（24.9 vs ~12ns，alloc+free 的固定开销），但那不是真实批量的量级。
> ⇒ 上一节那条「C 是唯一没有所有权陷阱的形态」**现在有了数字支撑**：
> **选 C 不付任何性能代价，却拿掉两个正确性风险。**

## 三种回传形态与它们的代价

| 形态 | 谁拥有内存 | 何时释放 | 代价 |
|---|---|---|---|
| **A 回传指针**（借用） | **Rust**（静态缓冲） | Rust 进程退出，或**下次调用被覆盖** | 最省 |
| **B 拷贝**（Rust 分配） | **Rust**（`std::alloc`） | 调用方**必须**显式 `free_buffer` | 中 |
| **C 写进 Java 堆外缓冲** | **Java**（`Arena`） | Arena 关闭时 | 两侧都不分配 |

🔴 **三者做的工作必须完全相同**，否则差值里就混进「工作量不同」这种噪声。
所以它们共用同一个 `transform_into`（`dst[i] = src[i] ^ 0x5A`）——
选它是因为**可逆**（Java 能独立算出同样结果做对拍）且**逐字节**（工作量与载荷成正比，
和真实实现「读一遍、改一遍」同形）。

## 🔴🔴 内存所有权模型（这一节比任何耗时数字都重要）

「回传指针」最省，但它的代价不在性能上，在**正确性**上。三种形态的所有权语义：

### A · 回传指针（借用）

```
Rust 持有：静态 Vec<u8> BORROW_BUF
  ↓ produce_borrow(src, len) 把结果写进去，返回长度
  ↓ borrow_buffer_ptr() 返回地址
Java 持有：一个 reinterpret 过的 MemorySegment 视图
```

- **谁的内存**：Rust。Java 只是拿了一个**视图**。
- **何时释放**：**没有显式释放**。但 🔴 **下一次 `produce_borrow` 会覆盖同一块内存**
  ⇒ 该指针**只在下一次调用前有效**。
- **能跨调用持有吗**：**不能**。持有就是 use-after-free。
- **真实实现必须做的事**：拿到结果后**立即消费或拷走**，不得缓存跨调用。
  这条约束必须写进接口契约，而不是靠注释提醒。
- 🔴 **若真要长期持有**：只能让 Rust 侧维护一个「多槽轮换 + 显式回收」的池
  （例如固定 N 个槽、槽满时回收最旧的），代价是**内存常驻 N × 载荷**，以及一次槽管理。
- **单线程假定**：`BORROW_BUF` 是进程级静态，**当前实现不支持并发调用**。
  真实实现若要并发，必须改成 thread-local 或加锁 —— 两者都会改变上面的所有权语义。

### B · 拷贝（Rust 分配）

```
produce_alloc(src, len) → Rust std::alloc(len) 一块，写入，返回指针
Java: reinterpret → 拷走 / 就地消费
free_buffer(ptr, len)   ← 必须成对调用
```

- **谁的内存**：Rust 分配的，但**所有权移交给调用方**（Java 拿到的指针）。
- **何时释放**：**只有** `free_buffer`。漏掉就是泄漏一块载荷大小的内存。
- **失败语义**：`produce_alloc` 返回 `0`（Rust 侧空指针）时，Java **不得**调 `free_buffer`。
- **风险**：配对纪律靠人。若要更稳，可以让 Rust 侧记账并在下次调用时报告「上次是否有泄漏」。

### C · 写进 Java 堆外缓冲

```
Java: Arena.allocate(len) 一次（可跨全部调用复用）
  ↓ produce_into_dst(dst, dst_cap, src, len)
Rust: 直接写进 Java 的内存
Java: 读同一个 segment
```

- **谁的内存**：**Java**。Rust 只是借用写入。
- **何时释放**：**Arena 关闭时**。没有配对调用，没有泄漏路径。
- **截断可检测**：`dst_cap < len` 时返回**实际写入量**而不是假装写满，
  调用方据此发现截断（单测 `into_dst_reports_truncation` 钉住）。
- **无生命周期风险**：不存在「指针下次就被覆盖」这回事。

### 🔖 结论

| | 所有权风险 | 泄漏风险 | 并发 |
|---|---|---|---|
| A 回传指针 | 🔴 **高**（跨调用即 use-after-free） | 无（不释放，但常驻） | 🔴 不支持（全局静态） |
| B 拷贝 | 低 | 🔴 **高**（漏 `free` 就漏） | 支持（每次独立分配） |
| C 写进 Java 缓冲 | **无** | **无** | 支持（各自持有） |

**C 是唯一没有所有权陷阱的形态。** A 与 B 各有一个「做对了没事、做错了就出事」的坑。
若实测显示三者**耗时**差异不大，则**应直接选 C** —— 用一点性能换掉两个正确性风险，
这与 §5 的「稳定优先于性能」一致。

## 🔖 同一个坑，两次被抓住的方式完全不同

本轮在**编译期**踩到两处，都是上一轮那个「签名多态」坑的老面孔：

| 这次（编译期） | 上一轮（运行期，静默） |
|---|---|
| 返回 `MemorySegment` 的句柄不能复用声明返回 `long` 的通用 `invoke()` | `invokeExact` 目标类型推断成 `()Object`，而句柄是 `()long` |
| javac **直接编译失败** | 每次调用抛 `WrongMethodTypeException`，**被吞掉后不崩**，只是安静地把「异常开销」记成「跨界开销」 |

> 🔖 **这是本文件最该带走的一条方法论**：
> **签名多态的错误，一部分能在编译期挡住；剩下的运行期表现是「不崩、只让数变假」。**
> 我上一轮拿到过明显不对的 `noop/cached = 641.8ns`，**是纯 Java 基线对照把它暴露的** ——
> 也就是说，如果没有那个基线，我大概会把「异常开销」当成「跨界开销」写进结论，而且看不出任何异常。
>
> ⇒ **纯 Java 基线对照不只是「扣掉循环开销」的工具，它还是「我的数是不是异常」的探测器。**
> 任何一个跨界微基准都应当有它，否则你测的可能根本不是你想测的东西。

（本轮还有一处编译期错误值得一提：`borrow_buffer_ptr` 用 `ValueLayout.ADDRESS` 声明时，
句柄**已经**返回 `MemorySegment`，外面再套 `MemorySegment.ofAddress(...)` 是错的 ——
那个重载收的是 `long` 地址。这类「FFM 语义记错」的错同样只在编译期暴露。）

## 测量方法学（沿用上一轮，已把坑都堵上）

| 要求 | 做法 | 上一轮的坑 |
|---|---|---|
| **强制冷访问** | 256MB 池 + 32MB（2×L3）步长轮转 + 非 2 的幂步进 | 忘了轮转 ⇒ **系统性低估**（失败方向最危险） |
| **同工纯 Java 基线** | 基线做**完全相同**的变换，不跨界 | 忘测基线 ⇒ 把循环开销算成跨界开销 |
| **四路和校验** | A / B / C / Java 四路结果必须一致，否则**停** | 有符号/无符号不一致 ⇒ 差值静默变噪声 |
| **夹具与被测分离** | 填充、分配都放在计时区外 | Arena 那次：填充被算成被测成本 |
| **换算用多档斜率** | 用 1MB/16MB 两档反推每字节斜率再外推 | 拿 64KB 档的数当 95,049 字节的数 |

计时区内的「消费」只读**首尾各一字节** —— 足以防死代码消除，又不会额外扫一遍内存。
完整校验和只在计时区**外**做一次。

### 一个必须记录的崩溃（形态 A 的真实代价）

**第一次跑直接 SIGABRT（JVM 崩在 `Unsafe_GetByte`）**，脚本的退出码后置校验抓到「零条数据」，
没有产出看似合理的假结果。根因：

- Rust 侧 `borrow_buffer_ptr()` 在缓冲还是 `Vec::new()` 时返回**悬垂指针**（不指向任何已分配内存）；
- 更深一层：原本按需 `resize`，**`Vec` 扩容会重分配**，⇒ **Java 缓存下来的地址随长度变化而失效**。

修法（两侧都改）：Rust 侧**首次 `produce` 时一次性按上限分配、永不重分配**，
越界请求直接返回 `0` 而不扩容；Java 侧**先 `produce` 再取指针**。
并补了 2 条单测钉住「长度变化不得改变缓冲地址」与「越界请求不得重分配」。

> 🔖 **这说明「缓存句柄」这个做法在形态 A 上有前提**：地址必须**真的稳定**。
> 上一轮实测「每次重取句柄贵一个数量级」，于是自然想缓存 —— 但在 A 形态下，
> **缓存的前提恰恰是最容易悄悄不成立的那个**。而它不成立时的表现是**段错误，不是变慢**。
> 形态 C 没有这个问题：缓冲由 Java 自己分配，地址天然稳定。

## 🔴 本文件**没有**证明的事

| 未覆盖 | 说明 |
|---|---|
| **「逐字节变换」是占位工作** | 能测出**跨界与传输**的代价，但**测不出真实 Rust 实现的内存访问模式**（分块扫描 vs 整份读可能相反） |
| **单线程** | 三种形态都在单线程下测；A 形态的全局静态**本来就不支持并发**，并发下的额外成本未测 |
| **只测了 64B–16MB 五档** | 真实整包 17,298,868 字节略超 16MB 档，斜率平坦外推可接受，但未直接测该尺寸 |
| **A 形态未测「多槽轮换」变体** | 那是为了跨调用持有而生的形态，代价（常驻内存 + 槽管理）未量化 |
| **未测跨平台 / 32 位长度路径** | 本实验单平台、64 位长度 |
| **35.5% 仍是上界** | §5.2 的 20% 阈值本就是为覆盖「构建链 + 四平台产物 + FFM 接线 + panic 边界防御 + ABI 维护」设的，**这些都还没发生** |
| **G1 仍未完成** | 转译相（Java 4190 行）与 `pack/` 解析相未移植 ⇒ 按 §5.1，**G3/G4 不得开始** |
