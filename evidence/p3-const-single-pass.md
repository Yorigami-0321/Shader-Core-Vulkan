## 改了什么

`ConstEvaluator` 拆成两条实现，由 `SINGLE_PASS` 开关选择：

- `evaluateSplit` —— 原实现：`split("\n",-1)` 物化整份行数组 + 每行 `strip()`；
- `evaluateSinglePass` —— 新实现：**不物化行数组**，按 `indexOf('\n')` 在原文上滚动行区间；
  先用下标扫出 `String.strip()` 的等价区间（复刻 `Character.isWhitespace` 语义），
  **只有前缀检查通过的行才 `substring` 一次**把真串交给正则。

冲突消解那段抽成共用的 `finish(...)`，保证两条实现的后半段口径一致。

留开关不是为了留后门，而是为了让**开与关在同一个二进制里** ——
否则要靠两个不同版本的时间点去比，机器状态不同、比值不可信（§7.3 的红线）。

## 等价性判据（X27：不许为性能砍 pack 特性）

const 产物不含文本，只能靠 `--dump-const` 的「选项 + 诊断」全量清单：

| 实现 | 选项 | 诊断 | 清单 sha256 |
|---|---:|---:|---|
| 原实现 | **51,336** | **0** | `1c7cfedde4119d61c…` |
| 单遍 | **51,336** | **0** | `1c7cfedde4119d61c…` |

**✅ 逐字节一致**，且与 P1 记录的基线哈希也相同（三方同哈希）。

**行边界口径**（单遍实现最容易错的不是正则，而是行数/行号）：
`split("\n",-1)` 后「丢一个末尾空串」被复刻为「文本以 `\n` 结尾 ⇒ 把最后一个换行符排除在扫描区间外」；
空文本两侧都是 0 行。新增 4 条单测钉死：行数口径、空白行**必须占行号**、
尾部 `\r` 按空白裁掉、行内含关键字但行首不是 ⇒ 不认。测试数 **612 → 616**。

## 为什么「35% 是 split/strip」却只省下 3%

P1 的 JFR 归因是**采样**（const 相 128 个样本），它给的是「时间花在哪个栈帧里」，
不是「这部分时间可以被消除」。两者差别在这里显形了：

- **分配的成本大头是 GC，而 GC 发生在别的线程上** —— 我按栈里含 `ConstEvaluator.evaluate`
  过滤采样，**GC 线程的栈根本不会被计入**，所以 `split`/`strip` 的真实总代价被低估了归属、
  高估了「可消除比例」；
- `split` 产生的是**短命年轻代对象**，bump 分配本身极快，JIT 的逃逸分析还能吃掉一部分；
- 而真正跑不掉的是：311,902 次行迭代 + 65,120 次前缀通过后的 `substring` + 正则入口。

⇒ **这不是实现写错了，是「JFR 采样占比」不能直接当「可优化空间」用。**
这条教训比那 3.0% 本身更值钱。

## 对决策的影响

| 观察 | 含义 |
|---|---|
| Java 侧微优化 const 到此为止（累计 7.5%） | 「靠便宜的 Java 改动解决 const」这条路**已排除** |
| 剩余成本是行迭代 + 65k 次 substring + 正则入口 | Rust 在这里**没有** inc 那样的「跳过正则」优势可吃（inc 的 4× 正是这么来的） |
| 227.6ms 仍是预处理段最大的一块 | **const 移植与否仍需裁决**，但天平进一步偏向「不值得为它单独上 Rust」 |

🔴 **本轮顺带暴露一个更值得注意的空白**：G0 的四段里，**`properties/options 解析` 占 43%
（约 681ms），是整条冷路径最大的单块，而它至今从未被 profile、也没有 G1 的 golden。**
在决定 const 之前，**那块更大、更黑**。

## 结论

1. ✅ 单遍实现已落地：**A/B 产物逐字节一致**、4 条行边界单测、留 A/B 开关。
2. ✅ 再省 **7.1ms / 3.0%**；P1 + P3 累计 **7.5%**。
3. 🔴 **Java 侧微优化 const 的路线到此为止**；且「JFR 采样占比 ≠ 可优化空间」这条教训已留痕。
4. ⏭️ 下一步优先级应重排：**先 profile `properties/options 解析`（43%，最大且全黑）**，
   而不是继续在 const 上找，或直接开 G1 转译相。
