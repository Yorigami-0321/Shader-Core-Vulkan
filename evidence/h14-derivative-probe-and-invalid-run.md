## 一、为什么顶点侧做不了，必须新增一个转译段

`h13` 定的候选 6 是：

~~~glsl
albedo = textureGrad(texture_0, newCoord, dcdx, dcdy) * vec4(color.rgb, 1.0);
~~~

而两个导数的声明**在片元里**（BSL 高级材质路径实测）：

~~~glsl
293: vec2 dcdx = dFdx(texCoord);
294: vec2 dcdy = dFdy(texCoord);
~~~

⇒ 顶点适配层够不着，只能在**转译阶段**做。新增第 **7¾ 段** `DerivativeProbeAdapter`，
排在 7½（槽位改写）之后、⑧（uniform 注入）之前。

**为什么这样改是干净的实验**：按 GLSL 规定，`textureGrad` 的两个显式导数参数为 0 时，
LOD 选取与 `texture()` 的隐式导数同为 0 ⇒ 采样结果**应当与 `texture()` 完全一致**。
所以「改写后画面是否变亮」是一个**干净的二值判据**。

## 二、🔴 单测当场抓到：探针**只对半个变量生效**

### 2.1 症状

~~~
DerivativeProbeAdapterTest > 开启：dcdx/dcdy 的右值换成 vec2(0.0)，其余行原样 FAILED
  org.opentest4j.AssertionFailedError: expected: <2> but was: <1>
~~~

### 2.2 根因

首版正则只写了 `dFdx`：

~~~java
"^(\\s*vec2\\s+(?:dcdx|dcdy)\\s*=\\s*)dFdx\\w*\\s*\\([^;]*?\\)\\s*(;.*)$"
~~~

而真实源码第 294 行是 **`dFdy`** ⇒ `dcdy` 那条**根本没被改**。

🔖 **为什么这条缺陷特别危险**：日志只报「已把 **N** 处」，N=1 看起来完全正常 ——
没有任何一处会提示「漏了 y 方向」。也就是说，这个实验会**安静地退化成半个变量**，
而结论仍然看起来像是「跑了实验」。**若无头断言，它会一路骗到发布。**

### 2.3 修法（两处）

1. 正则改为分别捕获**名字方向**与**函数方向**：`dc(dx|dy)` 与 `dF(dx|dy)`；
2. 命中后**再核对两者一致**（`dcdx↔dFdx`、`dcdy↔dFdy`），不一致就不改。

~~~java
if (matcher.matches() && matcher.group(2).equals(matcher.group(3))) { ... }
~~~

## 三、实现要点

| 项 | 做法 |
|---|---|
| 默认 | **关**（`mrt.terrainDerivativeProbe=false`），关闭时**逐字节恒等** |
| 作用域 | 只在生成地形片元源那段窗口打开，**`finally` 复位** |
| 等行数 | 只改右值、不增删行 ⇒ 转译链行号映射不受影响 |
| 保注释 | 行尾注释**原样捕获**（第 4 组），不会重演 X44「分号被吃掉」 |
| 不误伤 | 只认 `dcdx`/`dcdy` 两个名字，其它 `dFdx` 一律不动 |
| 自报（X45） | INFO 报「已把 N 处置零」；**N=0 时额外 WARN「开关没生效」** |

🔖 **`finally` 复位不是洁癖**：探针是**全局静态闸**，漏复位会让合成/延迟/最终四个程序的
转译也被改写（它们可能也声明 dcdx）⇒ 症状是「开了诊断开关之后别的画面也变了」，极难归因。

## 四、🔴 客户端那趟**作废**（这一节比结论重要）

### 4.1 发生了什么

本轮截图 `h14-K-derivative-probe.png` 看起来**完全正常**（沙漠、仙人掌、天空、云都对）。
🔖 **但它什么也证明不了**，三重原因叠加：

| 检查项 | 实测 |
|---|---|
| `terrain drawn into`（我方 pass 是否执行） | **0 次** |
| 探针自报（`派生导数探针`） | **0 次** |
| `mrt.terrainToMain` | **false**（本轮没开） |

⇒ 屏幕上的一直是**原版渲染**。原版永远看起来正常，**「画面正常」在这种配置下不含任何信息**。
真正的原因：这次启动里 **M-01 冷路径基准长时间占住渲染线程**（`hit x6250000` 仍在跑），
地形片元源从未生成 —— 也就是说，**探针连被调用的机会都没有**。

### 4.2 由此新增两条方法论（已登记）

**🔎 X46：取证前必须先证明「被测物确实在跑」。**
「画面看起来正常」是**最危险**的取证结果 —— 它和「一切正常」在像素上完全一样。
判据必须是**可数的日志行**（本项目用 `terrain drawn into N`），而不是观感。
🔖 这与 X9「先核实再断言」是同一条，但 X46 补上了它没覆盖的一半：
X9 说「要核实」，**X46 说「核实哪一行日志才算数」**。

**⏱ X47：M-01 冷路径基准会阻塞 runClient 的资源生成。**
实测本轮基准跑到 `hit x6250000` 仍未结束，期间地形片元源**一次都没生成**。
⇒ 想跑 `runClient` 取证，**必须先确认 M-01 已跑完**（日志里出现它的收尾行），否则这一趟白跑。
🔖 这与「不要并发基准和 runClient」是同一族问题的**同进程版本**：不是并发，是**先后**。
