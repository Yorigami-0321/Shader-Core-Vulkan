## 🔴 口径：§5.2 的阈值必须对**整条冷路径**算

§5.2 的原文是「**Rust 端到端中位数** 快 ≥ 20%」——
**端到端**，不是「预处理那一段」。

这一点不能含糊：`evidence/g3-preliminary-phase-comparison.md` 的假设表算的是
「Rust 预处理三段 vs Java 预处理三段」，**分母只有预处理**。而 §5.2 要的分母是**整条冷路径**
（包扫描 + 加载与预处理 + 转译）。若拿预处理内的快慢去对照 20% 阈值，就是拿小分母比大阈值。

因此本文件的算式一律是：

```
端到端快 (%) = (Java 端到端 − Rust 端到端) ÷ Java 端到端
```

## 判定表：四种情形 × §5.2

> 四种情形的差别**只有一个**：`const`（228.1ms，占预处理 49%）归谁、按什么速度跑。
> 端到端基准固定 895.3ms；除 const 外，其余环节两侧相同（Rust 完全没碰过它们）。

| 情形 | const 的归属与假设 | 端到端节省 | 端到端快 | §5.2 落在哪一行 |
|---|---|---:|---:|---|
| **S1** | **不移植**（当前 G1 范围：只移植 inc+def） | 78.4 ms | **+8.8%** | 🟡 快 5%–20% ⇒ **暂缓** |
| **S2** | 移植，且拿到 **inc 的 4.01×**（乐观） | 249.7 ms | **+27.9%** | ✅ 快 ≥20% ⇒ 落「采用」行 |
| **S3** | 移植，但只有 **def 的 1.55×**（保守） | −46.1 ms | **−5.2%** | ❌ **Rust 慢** ⇒ 不采用 |
| **S4** | **全不采用**（下界，不做任何移植） | 0.0 ms | **0.0%** | ❌ 差异 <5% ⇒ 不采用 |

### 算式（全部可从上表原始数据复算）

```
S1 = (160.603 − 40.022) − (119.286 − 77.149) = 120.581 − 42.137 = 78.444 ms
   ⇒ 78.444 ÷ 895.3 = 8.8%

S2 = S1 + (228.092 − 228.092 × 40.022/160.603)
   = 78.444 + (228.092 − 56.837) = 78.444 + 171.255 = 249.699 ms
   ⇒ 249.699 ÷ 895.3 = 27.9%

S3 = S1 − 228.092 × (119.286 − 77.149)/77.149
   = 78.444 − 228.092 × 0.5462 = 78.444 − 124.602 = −46.158 ms
   ⇒ −46.158 ÷ 895.3 = −5.2%（Rust 更慢）

S4 = 0 ms  ⇒ 0.0%
```

### 🔖 分解：只移植 inc 与「加上 def」的差别

| 方案 | 节省 | 端到端快 |
|---|---:|---:|
| **只移植 inc** | **120.6 ms** | **+13.5%** |
| **加上 def**（= S1 当前范围） | **78.4 ms** | **+8.8%** |
| | **差额 −42.1 ms** | **被 def 拖回 −4.7pp** |

⇒ **def 的负贡献吃掉了 42.1ms**（Rust 119.3 vs Java 77.1）。
**当前 G1 范围里唯一让数字变差的段就是 def** —— 这不是笔误，是首版实现的实测结果。

### ⚠️ def 那 1.55× 的限定（不可外推）

这测的是**本项目的首版移植实现**，**不是 Rust 语言的天花板**。
G3 前置已排查过分配瓶颈（`replace_all_word_bounded` 改成全字节扫描 + 未命中不分配后，
118.2 → 118.3ms，纹丝不动）⇒ 成本在「逐字符推进 + 替换后重扫」的结构上。
一个结构不同的实现可能给出不同数字。**不许拿这 1.55× 论证「Rust 不行」** ——
能论证的只有「**这个实现**慢了」。

### 🔖 Round 9 的口径修正**不改变**本结论，但**改变了基准**

| | 是否影响本文件 |
|---|---|
| 旧四段表把预处理算两遍 | ❌ **不影响**。分相对照读的是 **golden**，Rust 侧本来就没有那一行重复计算；本文件比较的是「同一相的 Java 耗时 vs Rust 耗时」，两边的被测对象都没被算两遍 |
| 生产入口 1494.9 → 895.3 | ✅ **影响，且是全部影响所在**。§5.2 的分母变小 ⇒ 同样的绝对节省换算成百分比后**变大**（这正是不重算就会出错的地方） |

一句话：**Round 9 改的是「这些数字分别代表什么」，本文件的结论靠的是「基准从哪来」。**

## 🔖 本轮最值钱的一条教训（来自移植过程）

const 相的**首版实现测出 195ms（1.17×）**——形状上**正好落在「不采用」区间**。
拆开后发现慢的全是自己多做的：

1. `Result.text` 存 `String` ⇒ 每轮**整份 17MB 拷贝**（Java 是原样透传同一引用）；
2. 每个字段存 owned `String` ⇒ 5.1 万条 × 5 ≈ **25 万次分配/轮**；
3. `origin_of()` 返回 owned ⇒ 每条**克隆两次**文件名字符串。

改成**借用**输入文本与行号映射（与 Java `Matcher.group(n)` 本来就是子串的数据流一致）→ **50.2ms**。

> **教训**：重估节说「P1 已证 const 的成本在字符串分配」是对的，但**没说「分配的是谁的」**。
> 照着去省了 `split`/`strip` 的临时串，却在自己的数据结构上造了**更多**分配。
> 🔖 **别把上一轮的瓶颈当这一轮的瓶颈** —— 这条比那 4.62× 更该记住。

## 下一步：还 def 的账，而不是继续榨 const

def 单独吃掉 **45.6ms ≈ 端到端 5.1 个百分点**。若修到与 Java 持平：
27.7% → **约 32.8%**。而 const 已越过 20% 门槛，再榨它的边际收益很小。

⚠️ 但注意：def 是**同一个零依赖约束下的反例**（快 4.62× 与慢 1.59× 在同一门语言里并存），
所以「修 def」之前得先弄清它慢在哪 —— 不能假设「换个写法就快」。
