## 二、实验设计

配置基线（`/tmp/r10-base.toml`）。两组之间**只改** `pack.capabilityGate`，
但🔖 **两组都把 `mrt.terrainToMain` 从 `false` 改成 `true`**（相对基线）——
因为 GAP-008 的黑屏**只在主目标上可见**（`terrainToMain=false` 时用户看到的仍是原版画面，
我们那套 colortex 根本不进屏幕）。

```
G1: terrainToMain=true, capabilityGate=false
G2: terrainToMain=true, capabilityGate=true
```

观测面与 `h31` 一致（都是**主目标**），而不是诊断视图 ——
🔖 `h31` 自己就因为 `h28`/`h29` 误用诊断视图下过结论，这里刻意避同一个坑。

## 四、🔴 本轮推翻的东西，与推翻的**边界**

### 4.1 被推翻的

`13-GAP-REGISTRY` GAP-008 的收尾（`h31`）写着：

> 关掉 `PARALLAX` 后 luma `0.0000` → `96.1485`、「地形全黑」是**真的**，
> 且**关掉视差即可消除**。

**在 Vulkan 上不成立**：G2 里 `PARALLAX=false` 已生效，主目标**仍然全黑**。

### 4.2 🔖 **不能**由此下的结论（本轮拒绝下的）

🔴 **G1 与 G2 不是单变量对照。** 门控不是「只关视差」，它关掉 **9 个**选项
并**改变了派生程序形状**：

| | G1（门控关） | G2（门控开） |
|---|---|---|
| `outputs` | **8** | **1** |
| `samplers` | **7** | **5** |
| `varyings` | **15** | **9** |

⇒ 因此**不能说**「视差无关」，也**不能说**「是那另外 8 个选项导致的」。
唯一站得住的是：
> **`h31` 依据的那个具体动作（关视差 ⇒ 消除黑屏），在本机 Vulkan 上没有得到证实。**

### 4.3 另一个必须登记的观测面事实

`mrt.terrainToMain` 的配置注释原文：「**会清掉主目标画面**」。
⇒ 两组黑屏里，**至少有一部分**可能是「清屏了但我们的地形 draw 没有落到主目标」，
而不是「包的地形片元输出全黑」。🔖 **这两者本轮没有分开**，
而要分开它需要一个判别手段（例如只让地形 pass 的附件 0 接主目标、
或在 draw 前后读回主目标）—— **已登记为下一步**，不假装已坐实。
