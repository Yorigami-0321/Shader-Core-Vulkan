# G0 口径修正 —— 分段表从四段改三段，并加「口径交叉校验」自检

> 承接 `evidence/pp-parse-profile.md` 与 `evidence/client-verify-preprocess-reuse.md`，
> 两者都登记了「**G0 四段表尚未修正**」。本轮修完。
>
> 修的不是数字，是**仪器本身** —— 之前两轮的工作重心都被它误导过。

## 为什么必须修

旧口径：

```
包扫描           = scan
properties 解析  = ShaderPackService.load(...)      ← 实测约 48% 是预处理，不是解析
#include 预处理   = Σ GlslPreprocessor.preprocess(...) ← **同一件事，又算一遍**
转译            = Σ OfGlslTranslator.translate(...)
合计(四段)       = 以上四段相加
```

`load` 为了提取 uniform / 属性声明，本就对每个阶段跑过一遍**完整的 `GlslPreprocessor`**；
旧表再把它单列一行加进合计 ⇒ **分段合计把预处理算了两遍**。

**失败模式很隐蔽**：每一段单独看都「合理」，只有合起来才露馅。
上一轮我们据「解析占 43%」把重心从 const 移开——那个数字正是被这个 bug 撑起来的。

## 改成什么样

```
包扫描             = scan
加载与预处理       = ShaderPackService.load(discovered, sink)   → pack + 逐阶段预处理产物
转译（8 段流水线） = Σ OfGlslTranslator.translate(stage, sink 里的预处理产物)
合计（分段三段）   = 以上三段之和
合计（生产入口）   = ShaderPackCompiler.compile(discovered)   ← 另起一趟
```

两处关键改动：

1. **预处理不再单列**，因为它已经含在「加载与预处理」里；段名也从「properties/options 解析」
   改成「加载与预处理」——**名字不能继续骗人**。
2. **转译段的输入直接取自 `load` 交出的预处理产物**（上一轮为复用加的 sink），
   于是既不重复计算，又保证**转译吃到的输入与生产路径完全同源**。
   `load` 若跳过某阶段（源文件不可读，Program 契约允许降级）则退回自算，并**显式告警**。

## 新增：口径交叉校验（让表自己证明没漂）

报告里现在固定带一行：

```
> 口径交叉校验：分段三段合计 872.1ms vs 生产入口 895.3ms，差 +23.2ms（+2.7%）—— ✅ 口径自洽
```

**为什么这道自检是必需的**：旧口径的错误正是「每段都合理、合起来偏大」。
光看单段发现不了；有了它，口径一漂报告就自己喊。

容差取 **±25%**，理由是两头夹逼：
- 下限：实测同机同构建这段差值在 **−3.8% ~ +12.1%** 间摆，阈值太低会误报；
- 上限：要防的「预处理算两遍」会表现为 **+48%**（463/1460），阈值太高就抓不住。

> 这道自检**当场抓出了我自己的 bug**：第一版自检拿「阶段数」和 `pack.programs().size()`
> 比（程序数 ≠ 阶段数，一个程序有 VERTEX/FRAGMENT 两阶段），
> 于是报了荒谬的「复用 182/91 个阶段」。修正分母后不再报警。
> —— 这正是自检该干的事：**让口径错误当场暴露，而不是等人看百分比才发现**。

## 修正后的数据（n=21，预热 3，BSL 182 阶段）

| 环节 | 中位数(ms) | p95(ms) | 占合计 |
|---|---:|---:|---:|
| 包扫描 | 0.5 | 0.8 | 0.1% |
| **加载与预处理** | **635.1** | 708.0 | **72.8%** |
| **转译（8 段流水线）** | **226.5** | 339.8 | **26.0%** |
| 合计（分段三段） | 872.1 | 1051.8 | 100% |
| 合计（生产入口） | 895.3 | 997.9 | — |

**口径交叉校验 +2.7% ✅**（旧表在同等条件下会明显偏大）。

> 注：生产入口从 G0 原始记录的 1494.9ms 降到 895.3ms，**主因是上一轮的预处理复用优化，
> 不是本轮的口径修正**；本轮改的是「这些数字分别代表什么」。

预处理内部分解（①`#include` 展开 / ②宏与条件编译 / ③选项常量扫描）仍在 `--phase-timing` 里，
但证据文件里明确标注：**它们是「加载与预处理」的子集，不可与上表相加**。

## 🔴 本文件**没有**证明的事

| 未覆盖 | 说明 |
|---|---|
| **没有重做统计检验** | 本轮是口径修正，不是性能结论；n=21 仍属小样本，跨轮极差 ±9% 的红线依旧适用 |
| **单包** | 只有 BSL；其它包的段占比会不同 |
| **没有验证 G1/Rust 侧是否也需要同步改口径** | Rust 侧读的是 `.inc.glsl` / `.pre.glsl` golden，**不受本轮影响**（它本来就没有「重复计算」那一行） |
| **`PackCompileCache` / 切包路径未涉及** | 本轮只修冷启动路径的分段口径 |

## 结论

1. ✅ 分段表**四段 → 三段**，预处理不再被重复计入，段名不再骗人。
2. ✅ 转译段改用 `load` 的预处理产物 ⇒ 与生产路径同源。
3. ✅ 新增**口径交叉校验**（容差 ±25%），并当场抓出我自己写错的分母。
4. ⚠️ 这轮改的是**仪器**，所有基于旧四段表的历史结论都应重新审视
   —— 尤其是「解析占 43%」与「预处理占 35%」这两个被反复引用过的数字。
