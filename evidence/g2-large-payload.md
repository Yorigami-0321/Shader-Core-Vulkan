# G2 补充 · 大载荷 FFM 传输开销 —— 按批 5.917ms，36.3% → 35.7%

> 补上 G2 **唯一没测的运行时代价**：上一轮只测了 40 字节载荷，而真实批次传的是
> **数十 KB～MB 的整份源码**（BSL 单阶段 ~95KB，整包 182 阶段合计 17,298,868 字节）。
> 载荷大一个量级以上时，「零拷贝传指针」的前提是否还成立，**必须实测**。

## 🔴 结论先行

**按批粒度 + 大载荷下，36.3% 的端到端收益剩 35.7%（零拷贝）/ 35.0%（拷贝）。**
只掉了 **0.6 个百分点**，**不影响 §5.2 的判定**。

但真正值得记的不是这个数，而是这句话：

> 🔖 **这 5.917ms 里，跨界机制本身只占 0.009ms**（550 次 × 15.7ns）。
> 其余是「**读这些字节**」的工作量 —— 真实实现无论跨界与否都要读，所以它**不是跨界开销**。

**载荷变大不增加跨界成本，增加的是内存读取的工作量。** 而那份工作
Rust 做得**更快**（见下），所以大载荷不但不吃掉收益，反而略微放大 Rust 的优势。

## 🔴 让这个实验能成立的三个前提（不满足就会得出更乐观的数）

### ① 必须强制冷访问，否则会**系统性低估**跨界成本

本机 **L3 = 16MB**。若反复对同一个 `MemorySegment` 调用，它会一直留在 cache 里，
测到的是「热缓存下传指针」的成本；而真实流水线每个阶段的缓冲区是**刚出来的**，
第一次触碰时是冷的。

做法：**256MB 缓冲区池 + 32MB（2×L3）轮转步长**，每档每轮把池子扫一遍，
并用**非 2 的幂步进**（`idx×3 + payload/64`）避免硬件预取把整段提前拉进缓存。

> 这是本任务最容易犯、且**失败方向最危险**的错误：忘了轮转 ⇒ 系统性低估。

### ② 必须有**同工**纯 Java 基线

基线 = 对**同一段内存**做**同样的字节和**，完全不跨边界。
若基线什么都不做，差值里就混进「Rust 干活的时间」，测到的不是跨界成本。
上一轮踩过「忘测基线 ⇒ 把 ~20ns 循环开销算成跨界开销」的坑，这里进一步要求**干同样的活**。

### ③ 每档开始前先校验三路和相等

`零拷贝 / 拷贝 / Java` 三路的校验和必须一致，否则差值没有意义。

🔴 **这道自检当场抓到一个真 bug**：Rust 侧是 `*b as usize`（无符号 0..255），
而 Java 的 `MemorySegment.get(JAVA_BYTE, i)` 返回**有符号** byte（−128..127）
⇒ 同工基线算的根本不是同一个数，报 `零拷贝=8160 拷贝=8160 Java=−32`。
修法是 `& 0xFF`。

> 🔖 **这比上一轮那次 `WrongMethodTypeException` 更值得记**：那次是「异常被吞掉后，
> 安静地把异常开销记成跨界开销」；这次是「两边算的不是同一件事，
> 差值静默地变成噪声」。**两者都不会崩，只会让数变假。**
> ⇒ **自检必须比性能数字先发现问题**，否则你拿到的是一个看起来很合理的错数。

### 🔴 最重要的一列：净跨界 = 零拷贝 − 同工基线

| 载荷 | 净跨界 | 含义 |
|---|---:|---|
| 64B | **+1.2 ns** | 几乎持平 |
| 1KB | **−98.0 ns** | Rust 更快 |
| 64KB | **−6,713.6 ns** | Rust 更快 |
| 1MB | **−111,461.9 ns** | Rust 更快 |
| 16MB | **−1,779,463.8 ns** | Rust 更快（1.94×） |

**从 1KB 起，净跨界就是负的** —— Rust 做同样的字节读取工作比 Java 快。
所以大载荷**不是**成本项；它把「读内存」这件事也算进来，而那件事**偏向 Rust**。

## 换算：36.3% 还剩多少

真实工作负载形状：整包 182 阶段、合计 17,298,868 字节、平均每批 ≈ **95,049 字节**、
按批 **550 次**跨界。

🔴 **换算方法必须说清楚，否则数是假的**：不能拿「64KB 档的耗时」直接当成
「95,049 字节那一批的代价」—— 那是把一个 65,536 字节的数错当成 95,049 字节的数。
正确做法是**反推每字节斜率**：在 64KB / 1MB / 16MB 上固定开销（~15.7ns）相对总耗时
已可忽略，于是 `ns/字节 ≈ 总耗时 ÷ 载荷字节`。

| 取样档 | 总耗时 | 载荷 | 斜率 |
|---|---:|---:|---:|
| 64KB | 7,643.0 ns | 65,536 | 0.1166 ns/字节 |
| 1MB | 117,707.0 ns | 1,048,576 | 0.1123 ns/字节 |
| 16MB | 1,896,057.9 ns | 16,777,216 | 0.1130 ns/字节 |

三档**独立反推高度一致**（0.1123–0.1166），这本身就是方法可信的旁证。
取中位 **0.1130 ns/字节**、固定开销 **15.7 ns/次**：

| 方案 | 每批 | ×550 次 | 端到端 |
|---|---:|---:|---:|
| **零拷贝** | 10,757.5 ns | **5.917 ms** | **35.7%** |
| 拷贝（Rust 先拷进 `Vec`） | 20,968.2 ns | 11.532 ms | 35.0% |

**36.3% → 35.7%，只掉 0.6 个百分点，不影响 §5.2 判定。**

其中**跨界机制本身只占 550 × 15.7ns = 0.009ms**；其余 5.908ms 是读字节的工作量。

## Arena：复用 vs 每批新建

🔴 **第一版这个对比是错的**，已修：最初只有 reuse / fresh 两臂，而 fresh 那一臂
每次都要 `fillDeterministic` **写 64KB** ⇒ 差值里混进了「写数据」的成本，
报出「新建比复用多 27,877.7ns/次 ⇒ 整包 15.3ms」—— **那个数不是 Arena 的成本**。
拆成三臂才能各自归因：

| 方式 | 中位数(ns/次) | p95 |
|---|---:|---:|
| `reuse`（预填充一次，之后只跨界） | 7,163.7 | 7,911.0 |
| `fresh-nofill`（每批 alloc + 跨界 + close，不填） | 7,880.3 | 8,840.7 |
| `fresh-fill`（每批 alloc + 填 + 跨界 + close） | 28,268.7 | 29,107.9 |

| 归因 | 计算 | 结果 |
|---|---|---:|
| **alloc + close** | `fresh-nofill − reuse` | **716.6 ns/次 ⇒ 整包 0.394 ms** |
| 填充（测试夹具产物，非真实管线成本） | `fresh-fill − fresh-nofill` | 20,388.4 ns/次 ⇒ 11.214 ms |

⇒ **Arena 复用与否几乎不用纠结**：整包差 0.394ms，相对 325.1ms 的收益可以忽略。
对照「拷贝 vs 零拷贝」的 6.505ms 差额 —— **拷贝与否更值得先定**（虽然两者都不致命）。

## 🔴 本文件**没有**证明的事

| 未覆盖 | 说明 |
|---|---|
| **读字节的占位工作不是真实工作** | 本实验用「字节和」代替真实解析。它能测出**跨界与传输**的代价，但**测不出真实 Rust 实现的内存访问模式**（例如分块扫描 vs 整份读）。真实解析可能有更好的缓存局部性，也可能更差 |
| **35.7% 仍是上界** | §5.2 的 20% 阈值本就是为覆盖「构建链 + 四平台产物 + FFM 接线 + panic 边界防御 + ABI 维护」设的，**这些都还没发生**。本文件只扣了运行时边界开销 |
| **未测回传开销** | 只测了 Java → Rust 单向。Rust 返回大结果（如整份新文本）的回传代价**未测** —— 而预处理产物**本来就是要回传的** |
| **未测并发跨界 / 跨平台 / 32 位长度路径** | 本实验单线程、单平台、64 位长度 |
| **`Arena` 泄漏只做了「每批 close」的结构性保证** | 未做「连续多趟后比对可用内存」的断言。结构性保证不等于实测无泄漏 |
| **只有 16,777,216 字节一档到顶** | 真实整包 17,298,868 字节略超 16MB 档，斜率已足够平坦，外推可接受，但**未直接测该尺寸** |
| **G1 仍未完成** | 转译相（Java 4190 行）与 `pack/` 解析相未移植 ⇒ 按 §5.1，**G3/G4 不得开始** |

## 结论

1. ✅ **按批 + 大载荷下，36.3% → 35.7%**（零拷贝）/ **35.0%**（拷贝）。**不影响 §5.2 判定。**
2. 🔖 **跨界机制本身与载荷大小无关**（15.7ns/次，恒定）；
   随载荷增长的是**读内存的工作量**，而那部分**偏向 Rust**（16MB 档快 1.94×）。
3. ✅ **五个档位全部可解读**（跨趟极差 ≤0.08×），上一轮 4.22× 的不可解读场景未复现。
4. ✅ **Arena 复用与否几乎无关**（整包 0.394ms）；**拷贝与否的差额更大**（6.505ms），但同样不致命。
5. 🔖 **两条方法论教训**：
   - **忘了轮转缓冲区 ⇒ 系统性低估跨界成本**（失败方向最危险的一类）；
   - **自检必须比性能数字先发现问题**：一次抓到「有符号/无符号不一致导致两路算的不是同一件事」，
     一次抓到「异常被吞掉后安静地把异常开销记成跨界开销」—— **两者都不崩，只让数变假**。
