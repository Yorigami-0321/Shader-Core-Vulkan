# G3 前置 · 分相对照数据（inc / def / const）—— Java vs Rust

> 🔴 **本文件不是 G3 裁决**。`17-NATIVE.md` §5.1 的流程是 G1 完成 → G2 → **G3 裁决**，
> 而 G1 还有**转译相**与 **`pack/` 解析相**未做。本文件是 **G3 的前置数据**：
> 把「两侧连同一个口径的数字都没有」这个状态终结掉，并据此给出**下一步该往哪投入**的判断。
>
> 上一版 G3 的阻塞理由原文：「Java 侧连 inc 单独计时都没有（G0 的预处理段是
> include+define+const 合并），两侧没有同一口径的数字可比。」—— 本文件正是来补这一条的。

## 口径对称性（本文件成立的前提）

Rust 侧两段各自**只做一件事**：

- `inc` = 源文件 → `#include` 展开产物
- `def` = inc 产物 → 宏与条件编译产物（直接读 golden 的 `.inc.glsl`）

所以 Java 侧也必须同样拆开：`def` 的输入是**计时外**算好并缓存的
`IncludeProcessor.Result`，否则 def 的耗时会混进 include 的工时，两侧就不是同一口径。
`--phase-timing` 另起一趟，**不覆盖** G0 的四段口径，历史数字继续可比。

另有自检：分相计时前逐阶段核对 inc / def 产物与 golden **逐字节一致**
（182/182 通过），确保「量到的」和「Rust 对齐的那个」是同一份工作。

## 数据（9 轮交替，跨轮统计）

| 相位 | 侧 | 中位数 | p95 | min | max | 跨轮极差 |
|---|---|---:|---:|---:|---:|---:|
| **inc** `#include` 展开 | Java | **158.8 ms** | 165.3 | 158.5 | 161.4 | 1.8% |
| **inc** | Rust | **39.6 ms** | 40.1 | 39.4 | 39.9 | 1.4% |
| | | **→ Rust 快 75.1%（4.01×）** | | | | |
| **def** 宏与条件编译 | Java | **76.4 ms** | 78.1 | 75.8 | 77.7 | 2.4% |
| **def** | Rust | **118.9 ms** | 125.1 | 118.0 | 121.4 | 2.8% |
| | | **→ Rust 慢 55.7%（1.56×）** | | | | |
| **const** 选项常量扫描 | Java | **243.9 ms** | 252.6 | 241.0 | 266.4 | 10.4% |
| **const** | Rust | **未移植** | | | | |

**Java 预处理三段合计 = 479.1 ms**。

> 交替协议确实把噪声压住了：inc / def 的跨轮极差只有 1.4%–2.8%，
> 远低于 G0 整趟测量的 ≈±9%（整趟含分配密集的解析段，抖动更大）。
> const 的 10.4% 明显更抖，值得留意（见下）。

## 这组数说明了什么

### ① `inc`：Rust 大赢，且赢在**该赢的地方**

Java 侧逐行跑 `Matcher.find()`（`^#\s*include\s+["']([^"']*)["']`），
每行都要进一次正则引擎；Rust 侧是手写字节扫描 + 边界断言。**4.01×** 的差距，
且 Rust 侧跨轮极差只有 1.4% —— 这个结论是稳的。

### ② `def`：Rust 反而慢 55.7%，而且**优化不掉**

Java 的 `replaceAll("\\b" + Pattern.quote(p) + "\\b", arg)` 走的是 JIT 编译过的正则引擎；
Rust 侧是手写的逐字符扫描 + 递归重扫。

⚠️ 我做了个排查：把 `replace_all_word_bounded` 从 `Vec<char>` 改成**全字节扫描 +
未命中不分配**，def 只从 118.2ms 变成 118.3ms —— **分配根本不是瓶颈**。
成本在 `expand_macros` 本身的「逐字符推进 + 每次替换后重新扫描」这个结构上。

🔴 **重要限定**：这测的是**我这个首版移植**，不是 Rust 语言的性能天花板。
一个结构不同的实现（比如不做替换后重扫）可能给出不同数字。**不许拿这 1.56× 去论证
「Rust 不行」** —— 能论证的只有「这个实现慢了」。

### ③ 🔴 最大的发现：最大的那块**根本没被移植**

`const`（选项常量扫描）**243.9ms，占预处理段的 51%**，是 inc+def 加起来（235.2ms）还多。
而它**不修改文本**（类注释原文：「本处理器**不修改**文本，文本原样透传」）——
纯扫描，只为发现选项常量。

也就是说：**G1 移植的两段，正好是预处理段里较小的 49%。**

### ④ 三种假设下，const 的归属决定一切

| 假设 | const 归谁 | Rust 总耗时 | vs Java 479.1ms | 对照 §5.2 的 20% 阈值 |
|---|---|---:|---:|---|
| A | 不移植，走 FFI 只跑 inc+def | 158.5 + 243.9 = **402.4ms** | **慢 16.0%**（更慢） | ❌ 连 20% 都不到 |
| B | 移植，按 inc 的 4.01× | 158.5 + 60.8 = **219.3ms** | **快 54.2%** | ✅ 远超阈值 |
| C | 移植，按 def 的 1.56×（保守） | 158.5 + 156.3 = **314.8ms** | **快 34.3%** | ✅ 超阈值 |

**A 与 B/C 之间是「不采用」与「采用」的分界**，而分界线正好压在最大的一块上。
换句话说：**在搞清 const 之前，讨论要不要上 Rust 是没有答案的。**

### ⑤ 还有一条更便宜的路：Java 侧的「先挡后正则」

`ConstEvaluator` 对**每一行**都无条件跑两条正则（`CONST_PATTERN` + `DEFINE_PATTERN`）
外加注释提取，约 190 万行次，绝大多数**立刻失配**。典型的廉价前置判断场景：

```
先 startsWith("const") / startsWith("#define") → 不满足就直接跳过正则
```

这是一个**纯 Java、小改动、低风险**的优化。如果它能砍掉大部分 243.9ms，
那么：同样的收益，不需要 FFI、不需要四平台产物、不需要 panic 边界防御、不需要未来 ABI 维护
—— 而这些正是 §5.2 里「20% 阈值必须显著大于的持续成本」。

> 本轮**不实施**这个优化（它是独立的一轮：改代码 + 重新取证 + 不得扰动 G0 基线），
> 但按 §7.1「先测后优」与 §1「参考先行」，它应当排在「移植 const」**之前**被评估。

## 结论与下一步

1. ✅ G3 的口径阻塞已解除：两侧现在有**同口径、分相对照**的数据（9 轮交替）。
2. ✅ `inc` 相 Rust 快 4.01× —— 这一段上 Rust 是明确赢家。
3. ⚠️ `def` 相 Rust 慢 1.56× —— 是**这个实现**慢，不是语言天花板，不可外推。
4. 🔴 **下一步不该直接去移植 4190 行的转译相**，而应先做两件事之一：
   - **P1**（更便宜、推荐先做）：实测 Java 侧「先挡后正则」能把 const 的 243.9ms 砍掉多少；
   - **P2**：决定 const 的归属（移植 / 不移植），因为它在假设 A 与 B/C 之间是分界线。
   这两件都做完，才知道该不该投入 G1 剩下的转译相。
