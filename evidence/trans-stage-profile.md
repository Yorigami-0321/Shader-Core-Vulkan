> **本轮只做评估，不做移植。** 目的是在动手前回答三个问题：

## 决策问题一：哪一段占大头？

**没有一段独大。** 分布比预处理**平得多**：

| | 最大段占比 | 前二 | 前三 |
|---|---:|---:|---:|
| 预处理（const/inc/def） | **const 49.7%** | 83.6% | — |
| **转译（8 段）** | **⑤ 31.5%** | **46.9%** | 57.0% |

⇒ **「只移植那一段」的收益上限就是段⑤ 的 31.5%（65.3ms）**，
远不如 inc/const 那种「一段占一半」的靶子清晰。

## 决策问题二：段的耦合有多紧？

🔖 **答案：耦合极松。任何子集都能独立移植。**

依据（全部来自签名，不是推测）：

1. **8 段全是 `String → String + 少量标量**，逐个核对 `Result` 记录：

   | 段 | `Result` 的额外字段 | 编排器实际消费哪些 |
   |---|---|---|
   | ①③④⑥ | 一个 `int` 计数 | 无（只取 text + diagnostics） |
   | ② | `renamedCount` | 无 |
   | ③ | `positionOperand` | 无（仅本段内部用） |
   | ⑤⑦⑧ | `insertIndex`, `insertedLineCount` | ✅ 这两个（喂行号映射） |
   | ⑦ | `insertedDeclarations` | 🔴 **不被消费** |
   | ⑧ | `injected: List<BuiltinUniform>` | 🔴 **不被消费** |

2. **`SourceLineMap` 一段都不碰。** 行号映射合成（`buildStageMap` /
   `buildCombinedStageMap` / `compose`）与诊断回填（`locate`）**全部在
   `OfGlslTranslator` 内、跑在 8 段之后**，只用到 ⑤⑦⑧ 的两个 int。

⇒ **FFI 面就是「整份文本 + ≤2 个 int」**，且是批量（整阶段一次），符合 T18。

**边界成本**（用 G2 实测的 54.0ns/次）：移植 k 段 ⇒ 182 × k × 2 次跨界。
k=1 → 364 次 ≈ 0.020ms；k=3 → 1092 次 ≈ 0.059ms。**相对 65–200ms 的段耗时可忽略。**

## 决策问题三：哪一段最可能「Rust 天然快」？

**段⑤ `LegacyBuiltinInjector`（65.3ms，占 31.5%）** —— 理由是它的**工作形态**：

```java
// LegacyBuiltinInjector.isUsed() —— 对每个旧名，扫一遍全部行
for (int index = 0; index < codeLines.size(); index++) {
    String line = codeLines.get(index);
    int at = line.indexOf(name);          // ← 重复子串搜索
    while (at >= 0) { … at = line.indexOf(name, at + 1); }
}
```

它被调用于 **9 个 RENAMES + `TEXTURE_MATRIX_LEGACY` + 11 个 INJECTIONS**（去重后约 **21 个名字**），
**每个名字都把约 2400 行扫一遍** ⇒ 182 阶段合计约 **920 万次行扫描**，
每次至少一次 `indexOf`；外加 `isDeclared()` 对每个注入候选逐行跑 **2 条正则**。

这正是 inc 相「字节扫描替代正则 + 重复子串搜索」赢下 **3.28×** 的同一形态。

其次是段②（32.0ms，15.4%）：但它**本来就是手写扫描、零正则**，
算法形态与 Java 相同 ⇒ Rust 的优势来源少一些（不是「跳过正则」，而是别的东西）。

⚠️ 反过来看：①③④⑥⑦⑧ 里有 4 段已经是手写扫描（①③⑦ + ⑤ 主体），
**这类段 Rust 不一定有优势** —— 别把 inc 的结论套到它们头上
（Round 11 的教训：**别把上一处的结论当这一处的结论**）。

## 移植范围建议

以 **Rust 已验证的速度**（inc 3.28× / const 4.67× / def 1.75×）做上界估算：

| 范围 | 需要移植的 Java 行数 | 假设速度 | 端到端增益 | 大概几轮 |
|---|---:|---:|---:|---:|
| 只做⑤ | 约 1050（531+232+163+124，含依赖工具） | 3× | **+4.9%** | 2–3 |
| ⑤+② | 约 1700 | 3× | **+7.2%** | 3–4 |
| 全部 8 段 | **4190** | 3× | **+14.7%** | 8–12 |

（增益 = 段耗时 × (1 − 1/3) ÷ 895.3ms。FFI 边界成本已按 G2 实测扣除，可忽略。）

### 🔴 结论：**不建议现在做转译相**

三条理由，按权重：

1. **门槛已经过了。** 预处理三相移植已让端到端达 **36.3%**（§5.2 阈值 20%）。
   转译相**全量移植**再加 **≈14.7%**，是**锦上添花，不是过门槛的必要条件**。
2. **性价比明显低于已完成的预处理。** 预处理三相（inc/def/const + `SourceLineMap`）
   约 2400 行换来 **36.3%**；转译相 4190 行（**1.7 倍**）只换来 **14.7%**。
   单位行数的收益是前者的 **1/3.6**。
3. **风险不对称。** 转译相直接产出**下游要编译的 GLSL**（X27：绝不以砍 pack 特性换性能）。
   预处理出错会体现在选项/声明提取，转译出错是**画面不对**。
   在门槛已过的情况下，为 14.7% 承担这个风险不划算。

### 什么情况下值得重开这个决定

- 若 §5.2 的裁决结论是「采用」且要求**把 26% 的转译相也拿掉**（例如为了消除 Java 侧的
  那 226–251ms 本身）——那就不是优化而是**消除单点**，理由会不同；
- 若后续发现预处理某一相出现回归，需要转译相作为**新的收益来源**；
- 若 §5.4 的「持续成本」清单被证明**低于**预估（构建链/四平台/ABI 维护其实很便宜），
  则 14.7% 的边际也值得。

